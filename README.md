# trip

여러 숙박 공급사의 상품을 하나의 모델로 통합해, 날짜와 인원으로 한 번에 검색하는 API 서버.

## 개요

숙박 공급사는 저마다 다른 방식으로 상품을 표현한다. 같은 객실이라도 A는 1박 요금과 세액을 날짜별로 나눠 주고, B는 기간 전체 총액을 세금 포함으로 한 번에 준다. 실패를 알리는 방법도 다르다. A는 HTTP 상태 코드로 알리지만, B는 장애 상황에서도 HTTP 200을 주고 본문 `resultCode`로만 알린다.

## 빠른 시작

JDK 25가 필요

공급사는 같은 저장소의 Mock 모듈을 호출

```bash
# 1) 공급사 Mock (9090) 
./gradlew :mock-supplier:bootRun

# 2) 애플리케이션 (8080)
./gradlew bootRun
```

```bash
# 3) 검색
curl "http://localhost:8080/api/v1/stays/search?checkIn=2026-10-01&checkOut=2026-10-04&adults=2&children=0"
```

## 프로젝트 구조

```
trip/
├── src/main/java/com/trip/
│   ├── stay/          숙소 도메인 (검색·동기화)
│   │   ├── controller/    요청 검증, 응답 변환
│   │   ├── business/      흐름 조립 (StayService)
│   │   ├── implement/     매핑 저장·조회 (StayManager, RoomTypeManager)
│   │   ├── dataaccess/    엔티티와 리포지토리
│   │   └── vo/            RoomOption → SearchedRoom
│   ├── supplier/      공급사 연동 경계
│   │   ├── a/ b/          공급사별 클라이언트와 응답 DTO
│   │   ├── global/        공통 호출기, 병렬 실행, 서킷 브레이커, 재시도
│   │   └── vo/            공급사 입력 모델
│   ├── support/       공통 예외·응답·값 타입
│   └── config/        WebClient, Executor, Swagger
└── mock-supplier/     공급사 A·B Mock (별도 모듈, 9090)
```

계층은 `controller → business → implement → dataaccess` 한 방향이고, 공급사 연동은 `com.trip.supplier`로 떼어 **도메인 → supplier 한 방향**으로만 의존한다. 공급사 응답 DTO는 `supplier` 패키지 밖으로 나가지 않는다.

### 1. 요금을 날짜별로 쪼개지 않고 숙박 기간 총액 하나로 둔 이유는?

**상황**
: A는 날짜별 1박 단가와 세액을 나눠 주고, B는 숙박 기간 전체 총액만 세금 포함으로 준다.

요금을 날짜별로 쪼개 표준에 담을지, 총액 하나로 접을지 정해야 한다.

**선택한 구조**
> 검색 결과 1건당 **숙박 기간 전체 총액**으로 보여준다.

**다른 후보와 문제점**
* **후보: 날짜별 요금으로 보여주는 경우**
  * B는 날짜별 요금이 주어지지 않으므로 임의로 날짜별 요금을 정해서 보여주면 정확한 요금이 아니기 때문에 안됨.
  * 사용자 입장에서 실제로 보고 싶은 건 금액의 최종값이라고 생각함. 
  * 연박으로 인해 가격의 변동성이 존재할 수 있지만, 궁금한 해당 날짜 범위를 다시 정해서 요청하면 된다고 생각함.

**선택 이유**
1. **두 공급사가 모두 줄 수 있는 유일한 형태** 
2. **고객이 비교하는 단위와 같음.**

### 2. 기준을 세금 포함 총액으로 잡은 이유는? 

**상황**
: A의 `nightlyRate`는 세금 별도이고 세액이 `taxAmount`로 따로 온다. 

B의 `totalPrice`는 세금 포함이고 세액은 알려주지 않는다. 기준을 어느 쪽으로 잡을지 정해야 했다.

**선택한 구조**
> **세금 포함 총액** 

**다른 후보와 문제점**
* **후보: 세금 별도 총액을 기준으로**
  * B는 세액을 주지 않으므로 세율을 내가 가정해서 계산해야 함. 
    * 추정값으로 사용자에게 제공하는 것은 값이 달라졌을 떄 신뢰성 문제로 이어진다고 생각함.

**선택 이유**
1. **양쪽 다 손실 없이 도달할 수 있는 유일한 기준**
   * A만 계산해서 보여주면됨
2. **고객이 낼 금액과 같음** 
   * 추가 계산이 없고, 결제 단계에서 값이 갑자기 오르지 않음
3. **정책 상 세금은 포함해서 보여줘야함**

### 3. A만 주는 날짜별 단가·세액을 살리지 않고 버린 이유는? 

**상황**
: A만 날짜별 단가와 세액을 준다. 이 값을 선택적으로라도 살릴지 정해야 했다.

**선택한 구조**
> **표준 응답 구조에 넣지 않는다.** 총액을 계산하는 용도로만 쓰고 응답으로 내보내지 않는다. 

**다른 후보와 문제점**
* **후보: A에서 온 상품에만 날짜별 요금 포함**
  * 어떤 상품에는 있고 어떤 상품에는 없는 필드가 생겨, 공급사 차이를 감추려고 만든 통합 모델인데 차이가 생겨버림
    * 여기서 B도 채우기 위해 일수로 나누게 되면, 또 임의로 결정한 금액이라 정확하지 않음

**선택 이유**
1. **한쪽만 주는 값을 표준에 올리는 순간 나머지 한쪽은 예측값이 되어버려서**
2. **날짜별 요금을 쓰는 기능이 없음**

### 4. 내부 식별자를 순번이 아니라 앱에서 만드는 UUID로 둔 이유는? 순번을 버린 대가는?

**상황**
: 숙소·객실 타입의 내부 식별자를 DB 순번(`IDENTITY`)으로 할지 UUID로 할지, UUID라면 DB와 앱 중 어디서 만들지 정해야 했다.

**선택한 구조**
> **`java.util.UUID`, 앱에서 생성**(`@UuidGenerator`) 

**다른 후보와 문제점**
* **후보: DB 순번 ID(`IDENTITY`)**
  * 정렬 가능한게 현재 상황에서는 크게 득될게 없다고 생각함.
    * 정렬/페이지는 요구사항에 없으므로
    * 인덱스 정하는 기준도 현재 상황에서는 명확하지 않음(데이터 분포, 데이터량 등 모르기 때문)
  * `IDENTITY` 는 JDBC에서 batch 작업이 안됨.


**선택 이유**
1. **정렬 안씀**
2. **앱 생성이라 INSERT 배치가 가능**
3. **보안상 유리**

### 5. "같은 공급사 상품은 항상 같은 식별자"를 무엇이 보장하는가?

**상황**
: 공급사 목록을 다시 동기화해도 같은 상품이 같은 내부 식별자로 돌아와야 한다. 무엇이 이를 보장하는지 정해야 했다.

**선택한 구조**
> **DB 제약 조건 + "조회 후 재사용" 동기화.**

**선택 이유**
1. 제약 조건으로 인해 애플리케이션 로직이 틀려도 DB가 중복을 거부
2. 멱등성이 보장되므로 되돌아온 숙소도 같은 행을 찾는다.

### 6. 유일 키를 (공급사, 숙소 코드)·(숙소, 객실 코드)로 잡은 이유는? JPA 연관관계 없이 FK 제약만 둔 이유는?

**상황**
: 공급사 코드의 유일성 범위가 서로 다르다. 
숙소 코드는 공급사 안에서만 유일하고, 객실 타입 코드는 **그 숙소 안에서만** 유일하다. 다른 숙소에 같은 객실 코드가 존재할 수 있다.

**선택한 구조**
> 숙소는 **`UNIQUE (supplier, stay_code)`**, 객실 타입은 **`UNIQUE (stay_id, room_type_code)`**. 
> 
> 객실 타입은 `@ManyToOne` 없이 `UUID stayId` 컬럼만 들고, 관계는 DDL의 `FOREIGN KEY` 제약으로만 표현한다.

**다른 후보와 문제점**

* **후보: `@ManyToOne` JPA 연관을 맺는다**
  * **지연 로딩 프록시와 N+1이 문제 우려**  

**선택 이유**
1. **유일 키가 공급사의 식별자 규칙을 지키기 위해**
2. **N+1 문제 방지**

### 7. 숙소·객실 목록을 매번 호출하는 게 아니라 앱 기동 1회 / 매일 새벽 4시 스케줄러 로 호출하는 이유는?

**상황**
: 재고·요금 API는 **숙소 코드 목록을 받아** 조회한다. 즉 어떤 숙소를 물어볼지 우리가 먼저 알고 있어야 한다. 그 목록을 매 검색마다 공급사에서 가져올지, 미리 저장하고 언제 호출할지 정해야 했다.

**선택한 구조**
> **셋 다.** 기동 시 1회 + 매일 04:00 + 수동 / 조회 시 `active` 컬럼을 기준으로 활성-비활성화 

**다른 후보와 문제점**
* **후보: 검색할 때마다 목록 API를 먼저 부른다**
  * 외부 호출이 2단계로 발생해, 목록 조회를 못하게 되면 요금 조회를 못하게 되고, 시스템 자원 고갈 위험이 있음.
  * 자주 안바뀌는 데이터이므로 매번 갱신할 필요는 없음.
* **후보: 기동 시 1회만**
  * 재배포까지 옛날 데이터
* **후보: 수동 API만**
  * 관리 부담
 

**주기를 하루로 잡은 근거**

* 숙소 목록은 자주 바뀌지 않는 데이터이고, 혹시 모를 변화에 대비하기 위해 사용자 수가 없는 새벽 시간에 동기화하는 것이 좋다고 판단
  * 새벽 시간에 장애가 발생 시, 다음 날에 수동으로 숙소 동기화

**선택 이유**

1. **인원 조건까지 DB에서 걸러** 모든 객실이 인원을 못 받는 숙소는 아예 묶음에서 빠짐.
2. 목록 조회는 하루에 한번 수행할 때 재시도로도 처리해도 됨.


### 9. 연박 검색에서 예약 가능 객실 수를 어떻게 판정하는가?

**상황**
: 연박 검색에서 "예약 가능 객실 수"를 어떻게 정의할지 정해야 했다. 공급사는 날짜별 잔여만 준다.

**선택한 구조**
> **요청 기간(체크인 ~ 체크아웃 전날) 날짜별 `remainingRooms`의 최솟값.** `Integer.MAX_VALUE`에서 시작해 날짜마다 `Math.min`을 접는다. 이 값이 0이면 예약 불가다.

**다른 후보와 문제점**
* **후보: 첫날(또는 마지막 날) 잔여를 쓴다**
  * ❌ **팔 수 없는 재고를 판다** — 1일 3실, 2일 0실이면 첫날 기준으로 3실이라고 답하지만 연박은 한 건도 불가능하다.
* **후보: 평균이나 합계를 쓴다**
  * ❌ **연박의 의미와 무관한 숫자다** — 3박 동안 매일 1실이면 합은 3이지만 팔 수 있는 건 1실이다.
* **후보: 하루라도 재고가 있으면 노출한다**
  * ❌ **요청한 기간을 통으로 묵을 수 없는 상품을 예약 가능으로 표시한다.**

**선택 이유**
1. **연박은 모든 날짜를 동시에 확보해야 성립한다.** 가장 적게 남은 날이 병목이고, 그 값이 곧 팔 수 있는 객실 수다.
2. **체크아웃 당일은 숙박일이 아니다** — 기간을 `checkIn.datesUntil(checkOut)`로 잡아 N박 = N일이 된다.
3. **0을 그대로 노출하는 결정(→ 10)과 맞물려** "있는데 안 남았다"를 정확히 표현한다.

### 10. 예약 불가 상품을 응답에서 빼지 않고 0으로 노출한 이유는? 남기면 무엇을 얻고 빼면 무엇을 잃는가?

**상황**
: 예약 가능 수가 0인 상품을 응답에서 뺄지, 0으로 노출할지 정해야 했다(명세가 어느 쪽이든 자유라고 둔 지점이다).

**선택한 구조**
> **0으로 노출한다.** 거르는 코드가 없다. 파생 불리언 `available` 필드도 두지 않는다.

**다른 후보와 문제점**
* **후보: 예약 불가 상품을 응답에서 뺀다**
  * ❌ **두 상황이 구별되지 않는다** — 고객 입장에서 "그 숙소는 우리가 안 판다"와 "파는데 그 날짜에 안 남았다"가 똑같이 빈 결과로 보인다. 뒤쪽이면 날짜를 바꿔 볼 수 있는데 그 정보가 사라진다.
  * ❌ **서버가 화면의 판단을 대신한다** — 나중에 "품절도 회색으로 보여줘"라는 요구가 오면 서버를 고쳐야 한다.
* **후보: `available: boolean` 파생 필드를 함께 둔다**
  * ❌ **같은 값을 두 번 준다** — `availableRooms > 0`과 항상 같고, 둘이 어긋났을 때 어느 쪽이 맞는지 계약에 없다.

**남기면 클라이언트가 얻는 것 / 빼면 잃는 것**
남기면 화면이 **품절 표시·날짜 변경 유도·대기 알림** 같은 선택지를 가진다. 빼면 그 상품이 애초에 존재하는지조차 알 수 없어, 고객은 "이 플랫폼에 그 숙소가 없다"고 판단하게 된다. 대가는 응답이 길어지는 것뿐이다.

**선택 이유**
1. **서버는 사실을 주고 표현은 화면이 정한다.**
2. **뺐다가 다시 넣는 판단을 서버가 대신하지 않는다.**
3. **같은 이유로 조건에 맞는 객실이 하나도 없어도 `rooms: []`로 200을 준다** — 결과 0건은 실패가 아니다.

### 11. 숙소 코드 50개 제한 아래에서 공급사는 병렬, 묶음은 순차로 부르는 이유는? 숙소가 수천 개가 되면?

**상황**
: 재고·요금 API는 한 번에 **숙소 코드 50개**까지만 받고, 넘기면 잘라 주는 게 아니라 요청 전체가 400이 된다. 숙소가 수천 개로 늘면 한 공급사에 수십 번 나눠 불러야 한다. 이 호출들을 어떻게 배치할지 정해야 했다.

> 요청에는 **객실 코드가 아예 실리지 않는다.** 어떤 객실을 팔지는 공급사가 응답으로 정한다. 따라서 묶는 단위도, 50이라는 상한도 숙소 기준이다. 응답 쪽에는 상한이 없어 결과 건수는 50보다 클 수 있다(숙소 하나가 객실 타입을 여럿 준다).

**선택한 구조**
> **공급사 간에만 병렬**(가상 스레드 Executor에 공급사당 태스크 1개), **한 공급사 안의 묶음은 순차 루프.** 상한 50과 분할은 `SupplierStayCodes`가 혼자 책임진다.

**다른 후보와 문제점**
* **후보: 묶음까지 전부 병렬로 던진다**
  * ❌ **동시 호출이 공급사 수 × 묶음 수로 폭발한다** — 숙소 3,000개면 공급사당 60개 묶음이라 한 번의 검색이 120개 동시 요청이 된다. 커넥션 풀(공급사당 50)을 즉시 고갈시키고 공급사의 호출 한도에 부딪친다.
  * ❌ **한 고객의 검색이 다른 고객의 검색을 굶긴다** — 풀이 한 요청에 점유된다.
* **후보: 공급사도 순차로 부른다**
  * ❌ **5초 예산 안에 못 들어온다** — A가 느리면 B는 시작도 못 한다. "한 곳이 늦어도 나머지로 응답"이 성립하지 않는다.

**선택 이유**
1. **실패와 지연의 단위가 공급사다.** 공급사 간 병렬만으로 "한 곳이 늦어도 나머지로 5초 안에 응답"이 지켜진다.
2. **순차 묶음은 자원 사용량을 예측 가능하게 만든다** — 공급사당 동시 1커넥션이라 동시 검색 수를 풀 크기로 가늠할 수 있다(→ 44).
3. **상한이 한 곳에만 있다** — 분할이 `partition` 정적 팩터리 하나에 모여 있어 호출부마다 50을 세지 않는다.

**숙소가 수천 개로 늘면**
지금 구조는 숙소 3,000개에서 공급사당 60번의 순차 호출이 되어 5초 예산을 넘긴다. 그때 바꿀 곳은 두 군데다 — **(1)** 검색 조건으로 후보를 줄인다(지역·키워드 필터가 들어오면 DB 단계에서 숙소가 걸러져 묶음 수가 준다). **(2)** 묶음을 제한된 동시성(예: 공급사당 4~8)으로 병렬화한다. 지금 순차로 둔 것은 현재 데이터에서 묶음이 1개뿐이라 병렬화의 이득이 0이고, 동시성 상한을 정할 근거(공급사 호출 한도)가 없기 때문이다.

### 12. 부분 실패를 HTTP 상태가 아니라 200 본문 `failures[]`로 표현한 이유는?

**상황**
: 검색은 공급사 N곳으로 나가는 fan-out이라 "A는 성공, B는 실패"가 정상적으로 일어난다. 이 상태를 HTTP로 어떻게 표현할지 정해야 했다.

**선택한 구조**
> **200 + 본문 `{ rooms[], failures[] }`.** `failures[]` 한 줄은 `(supplier, type, code)`이고 **공급사당 한 건**이다. 묶음 일부만 실패해도 그 공급사를 실패로 표시하되, 성공한 묶음의 상품은 `rooms[]`에 그대로 남는다.

**다른 후보와 문제점**
* **후보: 실패를 예외로 올려 HTTP 상태로 알린다**
  * ❌ **성공한 공급사의 결과까지 버려진다** — 타임아웃을 5초로 설계한 이유 자체가 무의미해진다.
  * ❌ **HTTP 상태는 하나뿐이라 일부 성공을 표현할 수 없다.**
* **후보: `207 Multi-Status`를 쓴다**
  * ❌ **WebDAV용 상태 코드**라 일반 REST 클라이언트가 해석하지 못하고, 본문 형식도 그쪽 규약을 따라야 한다.
* **후보: 묶음 단위로 실패를 싣는다**
  * ❌ **클라이언트가 우리 내부 분할 정책을 알아야 한다** — 묶음은 우리가 50개씩 자른 결과일 뿐 고객에게 의미 있는 단위가 아니다. 공급사 하나가 60개 묶음이면 `failures[]`가 60줄이 된다.

**묶음 일부만 실패해도 공급사를 실패로 표시하는 이유**
고객이 알아야 할 사실은 **"이 공급사의 결과가 완전하지 않다"**는 것 하나다. 어느 묶음이 빠졌는지는 내부 사정이고, 불완전한 목록을 완전한 것처럼 주지 않는 것이 핵심이다.

**선택 이유**
1. **검색은 성공·실패 이분법이 아니다.** 실패를 예외가 아니라 값으로 다뤄야 부분 성공을 표현할 수 있다.
2. **실패 단위가 고객이 이해하는 단위(공급사)와 같다.**
3. **값 타입을 새로 만들지 않았다** — 예외가 이미 같은 세 필드를 들고 있어 `toFailure()`가 그대로 변환한다.

### 13. 모든 공급사가 실패하면 200이 아니라 502를 내는 이유는? 실패 목록을 `data`에 실은 이유는?

**상황**
: 부분 실패를 200으로 표현하기로 했다면, **전부** 실패했을 때도 200이어야 하는지 정해야 했다.

**선택한 구조**
> **502.** 판정은 `호출한 공급사 수 > 0 && 실패 수 == 호출한 공급사 수`. 실패 목록(`List<SupplierFailure>`)을 오류 응답의 `data`에 그대로 싣는다(`E2006`).

**다른 후보와 문제점**
* **후보: `rooms: []` + `failures[]`로 200을 준다**
  * ❌ **"검색 성공, 결과 0건"과 구별되지 않는다** — 클라이언트가 `failures`의 길이를 직접 세어 판단해야 하고, 잊으면 장애가 "조건에 맞는 숙소 없음"으로 화면에 뜬다.
* **후보: "상품 0건 + 실패 1건 이상"이면 502**
  * ❌ **틀린 판정이다** — 한 공급사가 정상적으로 0건을 주고 다른 하나가 실패한 경우에도 502가 된다. 그건 부분 실패지 전체 실패가 아니다.
* **후보: 첫 실패 예외를 그대로 다시 던진다**
  * ❌ **공급사 하나의 정보만 남는다** — 예외의 `data`가 한 건으로 고정돼 있어 나머지 공급사의 실패 원인이 사라진다.

**실패 목록을 `data`에 실은 이유**
502만으로는 **왜** 실패했는지 알 수 없다. 공급사별 분류와 원본 코드가 함께 있어야 호출자가 재시도할지 판단하고, 우리도 로그 없이 응답만으로 원인을 좁힐 수 있다. 검증 실패가 `{필드: 사유}` 맵을 `data`에 담는 것과 같은 방식이다.

**선택 이유**
1. **결과 0건과 장애는 다른 사건이다.** HTTP 상태가 그 차이를 져야 한다.
2. **502(Bad Gateway)가 정확한 의미다** — 우리 잘못이 아니라 상류가 응답하지 못했다.
3. **판정에 "호출한 공급사 수"를 쓰면** 후보가 0건이라 아무도 호출하지 않은 경우(정상 200 + 빈 목록)와 구별된다.

### 14. A와 B의 같은 숙소를 합치지 않고 따로 노출한 이유는? 합치려면 무엇을 기준으로 써야 하고 그 기준이 왜 불안한가?

**상황**
: A의 한 숙소와 B의 한 숙소가 실제로는 같은 숙소·같은 객실일 수 있다. 그런데 **그 사실을 알려주는 공통 키가 스펙에 없다.** 하나로 합칠지 각각 노출할지 정해야 했다(선택 구현이다).

**선택한 구조**
> **합치지 않는다.** 공급사가 다르면 내부 식별자도 다른 두 상품으로 따로 노출하고, 각 줄에 `supplier`가 붙는다. 매칭 키에 `supplier`가 들어가 구조적으로도 갈린다.

**합치려면 무엇을 기준으로 써야 하고, 그 기준이 왜 불안한가**
공통 키가 없으니 **숙소명·객실 구성·주소 같은 값으로 추정**해야 한다. 그런데 추정이 틀리는 두 방향의 무게가 전혀 다르다.
- **못 합치는 쪽(false negative)** — 표기가 달라 같은 숙소를 못 알아보면 목록이 한 줄 길어질 뿐이다.
- **잘못 합치는 쪽(false positive)** — 이름이 비슷한 **다른** 숙소를 합치면 엉뚱한 숙소의 재고·요금을 보여주고, 예약까지 이어지면 사고다.

체인 호텔("○○호텔 강남점" / "○○호텔 역삼점")이나 표기 차이("Riverside Hotel Seoul" / "리버사이드 호텔 서울")를 생각하면 이름 유사도는 양방향으로 흔들린다. **되돌릴 수 없는 쪽의 위험이 훨씬 큰데 얻는 것은 목록이 짧아지는 것뿐이다.**

**조식 등 조건이 다른 상품을 같은 상품이라 부를 수 있는가**
**부를 수 없다.** 같은 객실이라도 A는 조식 미포함 429,000원, B는 조식 포함 452,000원이다. **값이 다른 게 아니라 조건이 다르다.** 합쳐서 한 줄로 만들면 어느 쪽을 남기든 고객이 비교할 선택지가 하나 사라지고, 싼 쪽을 남기면 "조식 포함이 더 좋았을 고객"의 선택지를, 비싼 쪽을 남기면 "싸게 자려던 고객"의 선택지를 없앤다. 조식 여부를 표준 필수 필드로 둔 것(→ 24)이 바로 이 두 줄을 구별하기 위해서다.

**다른 후보와 문제점**
* **후보: 이름 유사도로 합치고 먼저 도착한 쪽을 남긴다**
  * ❌ **같은 요청이 매번 다른 답을 준다** — 도착 순서는 공급사 응답 속도에 따라 바뀐다. 게다가 `invokeAll`은 제출 순서대로 결과를 돌려주므로 도착 순서 정보 자체가 없다.
* **후보: 공급사 우선순위를 고정해 합친다(A 우선 등)**
  * ❌ **결정적이 되기는 하지만 조건 차이 손실은 그대로다** — 항상 A의 조식 미포함 상품만 보이게 된다.

**선택 이유**
1. **틀렸을 때의 대가가 비대칭이다** — 안 합쳐서 생기는 손해는 목록 길이, 잘못 합쳐서 생기는 손해는 오예약이다.
2. **합치면 조건 차이가 사라진다** — 고객이 비교할 정보를 서버가 미리 버리는 셈이다.
3. **명세의 필수 요구는 "같은 공급사 상품이 항상 같은 식별자로 돌아오는 것"이지 공급사 간 통합이 아니다**(→ 5).
4. **대가는 같은 숙소가 두 줄로 보이는 것**이고, 정렬하지 않으므로(→ 38) 두 줄이 붙어 나오지도 않는다. 각 줄의 `supplier`와 `breakfastIncluded`가 차이를 설명한다.

### 15. 공급사 응답 형식이 도메인으로 새지 않게 무엇으로 막았는가?

**상황**
: A와 B의 응답 형식은 필드명도 구조도 다르다. 이 형식이 도메인 코드로 흘러들면 통합 모델이 무의미해진다.

**선택한 구조**
> **공급사 원본 DTO는 `supplier/{a,b}/response` 안에서만 산다.** 도메인(`com.trip.stay`)은 이 패키지를 단 한 번도 import하지 않는다. 변환은 Client가 아니라 **응답 record 자신**이 한다(`toSupplierStay()`·`toSupplierRooms(StayPeriod)`), 결과는 공용 VO(`SupplierStay`·`SupplierRoom`)다.

**다른 후보와 문제점**
* **후보: Client가 DTO를 받아 도메인 VO로 변환하는 별도 Mapper를 둔다**
  * ❌ **DTO를 아는 타입이 하나 더 는다** — 변환 규칙이 DTO의 필드 구조에 붙어 있는데 코드는 다른 파일에 있어, 응답 형식이 바뀌면 두 곳을 고쳐야 한다.
* **후보: 도메인이 공급사 DTO를 직접 받는다**
  * ❌ **모든 도메인 코드가 공급사 수만큼 분기한다** — 통합 모델을 만든 이유가 사라지고, 공급사가 늘 때마다 도메인이 뚱뚱해진다.

**선택 이유**
1. **변환 규칙이 그 형식을 아는 타입에 붙어 있다** — 응답 필드가 바뀌면 고칠 곳이 그 record 하나다.
2. **경계가 import로 검증 가능하다** — `supplier.a.response`를 도메인이 참조하는지는 grep 한 번으로 확인된다.
3. **도메인은 공급사가 몇이든 같은 타입만 본다.**

### 16. 의존 방향을 도메인 → `supplier` 한 방향으로 고정한 이유는?

**상황**
: 공급사 호출에는 기간·인원 같은 도메인스러운 값이 필요하다. 이 타입을 어디에 둘지에 따라 패키지 의존 방향이 갈린다.

**선택한 구조**
> **도메인이 `supplier`를 알고, `supplier`는 도메인을 모른다**(`supplier` → `com.trip.stay` import 0건). 공급사 호출에 실리는 입력 모델은 `stay/vo`가 아니라 **`supplier/vo`** 에 둔다(`SupplierStay`·`SupplierRoomType`·`SupplierRoom`·`SupplierStayCodes`·`SupplierFailure`). 양쪽에 다 필요한 `StayPeriod`·`Guests`는 **중립 자리(`support/vo`)** 에 둔다.

**다른 후보와 문제점**
* **후보: 입력 모델을 `stay/vo`에 둔다**
  * ❌ **`stay ⇄ supplier` 순환이 생긴다** — `supplier`가 그 VO를 쓰려면 도메인을 import해야 하는데, 도메인은 이미 `supplier`를 쓰고 있다.
* **후보: `supplier` 전용 조회 조건 record를 따로 만든다**
  * ❌ **필드가 같은 타입이 두 벌 생기고 변환 코드가 붙는다.**
* **후보: 원시값(`LocalDate`, `int`)을 그대로 넘긴다**
  * ❌ **시그니처에서 의미가 사라진다** — 날짜 두 개와 정수 두 개가 나열되면 순서를 틀려도 컴파일된다.

**선택 이유**
1. **순환 의존이 없어야 패키지가 경계로 기능한다.**
2. **기간·인원은 숙박 도메인 규칙이 아니라 일반 값이라 중립 자리가 맞다** — 타입이 한 벌만 남는다.
3. **인터페이스만 도메인에 두는 의존성 역전은 채택하지 않았다** — 공급사 연동이 도메인의 구현 세부가 아니라 별개의 경계라, 방향을 뒤집으면 오히려 어색하다.

### 17. 신규 공급사를 추가할 때 어디를 고쳐야 하는가?

**상황**
: 공급사 추가가 어디까지 번지는지 문서로 답할 수 있어야 한다.

**선택한 구조**
> **`SupplierClient` 인터페이스 + Spring의 `List<SupplierClient>` 주입.** 레지스트리나 팩토리가 없고, 비즈니스·컨트롤러에 공급사 분기가 없다.

**공급사 C를 추가할 때 손댈 곳 — 5군데, 전부 추가만**

| # | 위치 | 하는 일 |
|---|---|---|
| 1 | `supplier/Supplier` | enum 값 `C` 추가 (서킷·재시도·엔드포인트 맵의 키가 된다) |
| 2 | `supplier/c/SupplierCClient` | `SupplierClient` 구현. `SupplierHttpCaller`를 주입받아 요청 조립과 성공·실패 판정만 |
| 3 | `supplier/c/response/` | C의 응답 record + `toSupplierStay()`·`toSupplierRooms(StayPeriod)` 변환. 본문 코드 체계가 있으면 `CResultCode` |
| 4 | `config/supplier/WebClientConfig` | C 전용 커넥션 풀 빈 + `WebClient` 빈 |
| 5 | `application.yaml` | `supplier.endpoints.C.{base-url, api-key}` |

**고치지 않는 곳** — 도메인(`stay`) 전체, `SupplierDispatcher`, 서킷·재시도, 응답 계약, 검색 서비스. 새 빈이 `List<SupplierClient>`에 자동으로 들어가 병렬 호출 대상이 되고, 서킷·재시도 맵은 enum 값을 순회해 만들어진다.

**다른 후보와 문제점**
* **후보: `WebClient`를 공유하고 공급사별 빈을 만들지 않는다**
  * ❌ **커넥션 풀이 공유된다** — 한 공급사가 풀을 다 쓰면 다른 공급사 호출까지 대기에 걸려 "한 곳이 실패해도 나머지로 응답"과 어긋난다(→ 44).
* **후보: 팩토리로 `WebClient`를 동적으로 만든다**
  * ❌ **명시성과 공급사별 조정을 잃는다** — 빈 메서드 하나 추가를 감수하는 대신, 어떤 공급사가 어떤 설정을 쓰는지 설정 클래스에서 그대로 읽힌다.

**선택 이유**
1. **추가만 있고 수정이 없다** — 기존 공급사의 코드를 건드리지 않으므로 회귀 위험이 없다.
2. **Spring의 컬렉션 주입이 이미 레지스트리다** — 별도 등록 코드를 만들지 않는다.
3. **분기가 없다** — 공급사별 코드 묶기는 `groupingBy`로 하고 `if (supplier == A)` 형태의 분기를 두지 않는다.

### 18. WebFlux를 택하지 않은 이유는? 가상 스레드가 WebFlux의 이점을 어디까지 대체하고, MVC를 택한 대가는?

**상황**
: 여러 공급사를 동시에 호출하는 것이 이 서버의 핵심이다. 외부 호출은 `WebClient`로 하되, 웹 계층까지 리액티브로 갈지 정해야 했다.

**선택한 구조**
> **Spring MVC + 가상 스레드**(`spring.threads.virtual.enabled: true`). `WebClient`는 외부 호출에만 쓰고, 반환된 `Mono`는 **가상 스레드 위에서 `block()`으로 즉시 값으로 바꾼다.** `Mono`가 서비스·구현 계층으로 올라가지 않는다. 의존성에 WebFlux 스타터가 없다.

**다른 후보와 문제점**
* **후보: WebFlux로 전면 전환한다**
  * ❌ **JPA가 블로킹이다** — 매핑 조회가 블로킹 JDBC라 리액티브 체인 안에서 결국 스케줄러로 빼야 하고, 두 모델이 한 요청 안에 섞인다. R2DBC로 가면 JPA를 버려야 한다.
  * ❌ **스택 트레이스와 디버깅이 어려워진다** — 예외가 어느 단계에서 났는지 읽기 어렵고, 팀이 읽는 비용이 계속 든다.
  * ❌ **취소·타임아웃 의미를 다시 배워야 한다** — 지금은 `invokeAll` 하나가 마감·취소를 다 처리한다.

**가상 스레드가 WebFlux의 이점을 어디까지 대체하는가**
**대체하는 것** — 이 서버의 병목은 계산이 아니라 **외부 호출 대기**다. 가상 스레드는 블로킹 호출에서 캐리어 스레드를 놓아주므로, 플랫폼 스레드 풀이 외부 대기로 고갈되는 문제가 사라진다. 처리량 측면에서 우리가 WebFlux에 기대하던 이득은 대부분 여기서 나온다.
**대체하지 못하는 것** — **배압(backpressure)** 과 **스트리밍**이다. 리액티브의 요청량 협상이나 대용량 응답을 조각으로 흘려보내는 처리는 가상 스레드가 주지 않는다. 다만 이 서버는 응답을 통째로 받아 정규화하고 한 번에 내보내므로 둘 다 필요하지 않다. 배압 역할은 커넥션 풀 크기와 풀 대기 타임아웃이 대신한다(→ 44).

**MVC를 택한 대가**
요청당 스레드 모델이라 **동시성 상한이 자원 구성에 묶인다** — 커넥션 풀 50이 사실상 검색 동시성의 상한이 된다. 진짜 비동기였다면 커넥션 수와 동시 요청 수를 따로 조절할 수 있다. 또 `block()`을 쓰는 이상 **가상 스레드 위에서만 불러야 한다**는 제약을 코드가 계속 지켜야 한다.

**선택 이유**
1. **병목이 대기라서 가상 스레드로 충분하다.** 리액티브의 이득 중 우리가 실제로 쓰는 부분을 거의 다 가져온다.
2. **코드가 동기라서 읽힌다** — 타임아웃·취소·부분 실패 같은 까다로운 로직이 평범한 제어 흐름으로 표현된다.
3. **JPA를 그대로 쓸 수 있다.**

### 19. 연결 1s·응답 2s·전체 5s는 어떻게 정한 값인가? 개별 타임아웃과 별도로 전체 상한을 둔 이유는?

**상황**
: 외부 호출에 상한이 없으면 응답하지 않는 공급사 하나가 검색 전체를 잡는다. 어떤 층에 어떤 값을 걸지 정해야 했다.

**선택한 구조**
> **세 겹.** 연결 `1s`, 응답 `2s`, 검색 한 건의 전체 상한 `5s`. 여기에 커넥션 풀 대기 `200ms`, 유휴 커넥션 `30s`가 붙는다. 전부 `application.yaml`의 `supplier.*`에 있다.

| 층 | 값 | 거는 자리 |
|---|---|---|
| 풀 대기 | 200ms | `ConnectionProvider.pendingAcquireTimeout` |
| 연결 | 1s | 커넥터 설정 |
| 응답 | 2s | 커넥터 설정 + `Mono.timeout()` |
| **전체** | **5s** | `invokeAll(tasks, 5s)` |

**값의 근거**
- **전체 5s가 먼저다.** 고객이 검색 결과를 기다려 주는 한계를 5초로 보고, 나머지를 그 안에 들어가도록 역산했다.
- **연결 1s** — 같은 네트워크 안의 상대가 살아 있다면 연결은 훨씬 빨리 된다. 1초가 넘으면 살아 있지 않다고 보는 편이 맞고, 여기서 오래 기다릴수록 응답에 쓸 예산이 준다.
- **응답 2s** — **처음에는 3s였는데 2s로 줄였다.** 한 공급사의 묶음을 순차로 부르기 때문이다(→ 11). 최악이 `연결 + 응답 × 묶음 수`라, 3s면 묶음이 2개만 돼도 `1 + 3 × 2 = 7s`로 전체 상한을 넘긴다. 2s면 `1 + 2 × 2 = 5s`로 턱걸이한다.
- **풀 대기 200ms** — 풀이 비어 있다는 것은 우리 쪽이 포화됐다는 뜻이다. 오래 기다려 봐야 그 요청도 늦고 뒤 요청도 밀리므로, 빨리 실패해 백프레셔로 삼는다.
- **유휴 30s** — 상대가 먼저 끊은 커넥션을 재사용해 `Connection prematurely closed`가 나는 것을 막는다.

**개별 타임아웃과 별도로 전체 상한을 둔 이유**
개별 타임아웃은 **한 번의 HTTP 호출**에만 걸린다. 그런데 한 공급사는 묶음을 여러 번 부르고, 검색 한 건은 공급사 여러 곳으로 나간다. 개별 상한만으로는 **호출 횟수 × 개별 상한**이 전체 지연이 되어 상한이 없는 것과 마찬가지다. 전체 상한은 "고객이 기다리는 시간"이라는 다른 축의 약속이고, 개별 상한이 아무리 지켜져도 이 약속은 따로 지켜져야 한다. 초과한 태스크는 취소되고 `UNAVAILABLE / TOTAL_TIMEOUT_EXCEEDED`로 남는다.

**다른 후보와 문제점**
* **후보: 개별 타임아웃만 두고 전체 상한은 생략한다**
  * ❌ **묶음이 늘면 지연이 선형으로 는다** — 위 계산 그대로다.
* **후보: 전체 상한만 두고 개별은 생략한다**
  * ❌ **느린 공급사 하나가 예산을 다 쓰고 나머지도 같이 취소시킨다** — 개별 상한이 있어야 빨리 포기하고 다음으로 넘어간다.

### 20. A의 4xx/5xx, B의 `resultCode`, 타임아웃, 연결 실패를 하나의 분류로 묶은 이유는? 분류 축을 무엇으로 잡았는가?

**상황**
: A는 HTTP 상태로 실패를 알리고, B는 **장애 상황에서도 HTTP 200**을 주고 본문 `resultCode`로만 알린다. 여기에 타임아웃·연결 실패·파싱 실패까지 더하면 실패의 표현이 제각각이다. 도메인이 이 차이를 모르게 해야 한다.

**선택한 구조**
> **내부 분류 6개로 모은다** — `BAD_REQUEST` · `AUTH` · `RATE_LIMITED` · `UNAVAILABLE` · `INTERNAL` · `MALFORMED`. 두 어댑터 모두 **HTTP 상태 → 본문 파싱 → 본문 코드** 순으로 검사하고, 도메인에는 분류와 **원본 코드 문자열**만 전달한다.

| 실제로 일어난 일 | 내부 분류 | 원본 코드 예 |
|---|---|---|
| A가 HTTP 503 | `UNAVAILABLE` | `SERVICE_UNAVAILABLE` |
| B가 HTTP 200 + `resultCode: E503` | `UNAVAILABLE` | `E503` |
| 응답이 오지 않음 | `UNAVAILABLE` | `TIMEOUT` |
| 연결 자체가 안 됨 | `UNAVAILABLE` | `CONNECT_REFUSED` · `DNS` · `CONNECT_TIMEOUT` |
| 커넥션 풀 고갈 | `UNAVAILABLE` | `POOL_EXHAUSTED` |
| 서킷이 열려 있음 | `UNAVAILABLE` | `CIRCUIT_OPEN` |
| 401 / `E401` | `AUTH` | `UNAUTHORIZED` · `E401` |
| 429 / `E429` | `RATE_LIMITED` | `RATE_LIMIT_EXCEEDED` · `E429` |
| 본문을 해석할 수 없음 | `MALFORMED` | `UNPARSEABLE` · `EMPTY_BODY` · `NULL_DATA` |

**분류 축을 "재시도해도 되는가"로 잡은 이유**
분류가 존재하는 목적이 **판단**이기 때문이다. 이 분류를 보고 내리는 결정은 셋이다.
1. **재시도할까** — `indicatesSupplierDown()`(`UNAVAILABLE`·`INTERNAL`)만 재시도한다. `BAD_REQUEST`·`AUTH`는 다시 불러도 같고, `RATE_LIMITED`는 다시 부르면 상대를 더 때리며, `MALFORMED`는 상대가 응답은 하고 있다는 뜻이라 건강도 문제가 아니다.
2. **남은 묶음을 계속 부를까**(→ 34).
3. **서킷의 실패로 셀까** — 같은 `indicatesSupplierDown()`만 센다. 우리 요청이 잘못됐거나 응답 해석이 안 되는 것은 상대의 건강도가 아니다.

HTTP 상태를 그대로 쓰면 이 판단을 할 수 없다. B는 애초에 전부 200이고, 타임아웃과 연결 실패에는 상태 코드 자체가 없다. **"무엇이 일어났는가"가 아니라 "그래서 어떻게 할 것인가"로 축을 잡아야** 분류가 쓸모를 가진다.

**다른 후보와 문제점**
* **후보: HTTP 상태 코드를 그대로 도메인에 올린다**
  * ❌ **B의 실패가 전부 200으로 보인다** — 장애를 정상 응답으로 처리하게 된다.
  * ❌ **타임아웃·연결 실패를 표현할 코드가 없다.**
* **후보: 원본 코드를 그대로 도메인에 올린다**
  * ❌ **도메인이 공급사 수만큼 분기한다** — 공급사가 늘 때마다 재시도·서킷 판정 코드를 고쳐야 한다.
* **후보: 원본 코드를 버리고 분류만 남긴다**
  * ❌ **원인을 좁힐 수 없다** — `UNAVAILABLE` 하나로는 타임아웃인지 503인지 서킷인지 알 수 없어, 응답만 보고 디버깅할 수 없다.

**이 통일이 실제로 한 일**
A의 HTTP 503과 B의 HTTP 200 + `E503`이 **똑같이** 재시도되고(둘 다 2s·6s 대기 후 3회 시도) 똑같이 서킷 실패로 집계된다. 판정 코드에는 공급사 분기가 한 줄도 없다.

### 21. Mock을 컨트롤러·WireMock이 아니라 별도 Gradle 모듈 + 9090으로 둔 이유는?

**상황**
: 연동을 확인하려면 A·B를 흉내 내는 Mock이 필요하다. 테스트용 컨트롤러로 앱 안에 둘지, WireMock을 쓸지, 별도 모듈로 뺄지 정해야 했다.

**선택한 구조**
> **별도 Gradle 모듈 `mock-supplier`, 별도 프로세스, 9090 포트.** 의존성은 웹 스타터 하나뿐이고, 루트 앱은 이 모듈을 **의존하지 않는다** — 연결은 설정의 `base-url` 하나로만 이어진다.

**다른 후보와 문제점**
* **후보: 운영 앱 안에 테스트용 컨트롤러로 둔다**
  * ❌ **자기 자신을 HTTP로 부르게 된다** — 같은 프로세스에서 요청을 처리하며 자기 서버로 나가므로, 무응답 모드를 켜면 **스레드가 서로 물려 연동 문제로 오해하기 쉬운 실패**가 생긴다. 타임아웃 검증이 검증하려던 것과 다른 것을 재게 된다.
  * ❌ **운영 산출물에 Mock 코드가 섞인다** — 프로파일과 기능 끄기 설정으로 막아야 하고, 그 설정이 하나 틀리면 운영에 노출된다.
* **후보: WireMock으로 테스트 안에서만 띄운다**
  * ❌ **손으로 만져 볼 수 없다** — 애플리케이션을 띄운 채로 장애를 켜고 응답이 어떻게 변하는지 보는 것이 이 서버에서 확인해야 할 것인데, 테스트 수명 안에서만 사는 Mock으로는 불가능하다.
  * ❌ (다만 **통합 테스트에서는 `MockWebServer`를 쓴다** — 자동 검증과 수동 확인은 다른 도구가 맞는 자리다.)

**루트 앱이 이 모듈을 의존하지 않게 한 이유**
의존하는 순간 **운영 산출물에 Mock이 들어간다.** 컴파일 의존이 없으면 실수로라도 참조할 수 없고, 빌드 결과물에 섞일 수 없다. 또 공급사는 원래 남의 서버이므로 **HTTP 너머에만 존재하는 것이 실제 구조와 같다** — 주소만 바꾸면 진짜 공급사로 붙는다.

**선택 이유**
1. **프로세스가 갈려야 타임아웃·무응답 검증이 정확하다.**
2. **코드·의존성·산출물이 분리돼 프로파일이나 기능 끄기 설정이 필요 없다.**
3. **실제 연동 구조와 같은 모양이라** Mock에서 확인한 동작이 실제에서도 같다.

### 22. Mock은 무엇을 재현하고 무엇을 재현하지 않는가? 어떤 실패를 테스트로 고정하고 어떤 것을 수동 확인으로 남겼는가?

**상황**
: Mock은 채점 대상이 아니지만, 연동이 실제로 도는지 보여주는 유일한 수단이다. 어디까지 재현할지 정해야 했다.

**선택한 구조**
> **모드 3가지**(`normal` / `error` / `no-response`)를 **런타임 API**(`POST /control/{a|b}/mode?value=`)로 공급사별로 전환한다. 모드는 **네 엔드포인트 전부**(목록 A·B, 재고·요금 A·B)에 걸린다. 장애는 A가 HTTP 503, B가 HTTP 200 + `resultCode: E503`이다. 재고·요금 응답은 요청의 체크인·체크아웃을 읽어 **그 기간의 날짜로** 데이터를 만든다.

**모드 전환을 런타임 API로 둔 이유**
재시작 없이 바꿔야 **한 번 띄운 상태에서 정상 → 장애 → 복구를 이어서 볼 수 있다.** 특히 서킷 브레이커는 열림 → 10초 → 반열림 → 닫힘의 전이를 봐야 하는데, 이 시나리오는 프로세스를 살려 둔 채 모드만 바꿔야 관찰된다. 설정 파일이나 환경 변수로 두면 매번 재시작해야 하고, 그러면 서킷 상태가 초기화돼 아예 확인할 수 없다.

**목록 API에도 장애 모드를 건 이유**
**재시도는 목록 동기화에만 걸려 있다.** 목록에서 장애가 안 나면 재시도가 도는지 확인할 방법이 없다. 반대로 서킷 브레이커는 검색에만 걸려 있어 재고·요금 장애로 확인한다.

**재고·요금에 고정 날짜를 박지 않은 이유**
`StayPeriod`가 과거 체크인을 막으므로(→ 37) 고정된 과거 날짜로는 검색을 **호출조차 못 한다.** 미래 날짜를 박으면 요청 기간의 날짜가 응답에 없어 **모든 항목이 버려져**(→ 33) 연동이 도는지 확인할 수 없다. 요청 기간을 읽어 만들어야 검증이 성립한다.

**응답 지연을 별도 모드로 두지 않은 이유**
`no-response`가 600초를 재워 **사실상 무응답**이 된다. 전체 상한 5초보다 훨씬 길어 타임아웃 경로를 확실히 탄다. 여기에 "N초 지연" 모드를 더하려면 **경계값을 고를 근거**가 있어야 하는데(1.9초? 2.1초?), 그 경계는 이미 단위 테스트가 값으로 검증할 영역이지 손으로 확인할 영역이 아니다. Mock은 채점 대상이 아니므로 여기에 시간을 쓰지 않았다.

**무엇을 테스트로 고정하고 무엇을 수동 확인으로 남겼는가**

| | 자동 테스트 | 수동 확인(Mock) |
|---|---|---|
| **대상** | 값을 만들고 합치는 로직, 분기가 있는 정책 판정, 한도·경계 | 실제 프로세스 간 연동, 시간에 얽힌 동작 |
| **예** | 총액 합산·최솟값 계산, 날짜 누락 시 제외, B의 코드 → 내부 분류, 50개 경계, 부분 실패 응답 형태 | 부분 실패(A만 장애), 전체 실패 502, 무응답 시 타임아웃, 서킷 열림 → 반열림 → 닫힘, 동기화 재시도 |
| **이유** | 깨졌을 때 **조용히 틀린 값**을 내보내는 것들 | 실제 소켓·시간·상태 전이가 필요해 테스트로 고정하면 느리고 불안정해지는 것들 |

**다른 후보와 문제점**
* **후보: 장애 시나리오도 전부 통합 테스트로 고정한다**
  * ❌ **시간에 의존하는 테스트가 된다** — 서킷 열림 유지 10초를 기다리는 테스트는 느리고, 짧게 줄이면 실제 설정이 아닌 값을 검증하게 된다.
* **후보: Mock에 더 많은 실패 모드를 넣는다**
  * ❌ **채점 대상이 아닌 곳에 시간을 쓰는 것**이고, 근거 없는 경계값을 만들게 된다.

### 23. 재고는 왜 날짜별 값을 그대로 받는가? 요금과 성격이 어떻게 다른가?

**상황**
: 재고(`remainingRooms`)는 A·B 둘 다 날짜별로 준다. 요금처럼 공급사 응답 단계에서 하나로 접을지, 날짜별로 유지할지 정해야 했다.

**선택한 구조**
> **날짜별 값을 그대로 받아** 정규화 시점에만 기간 전체 기준 한 값(`availableRooms` = 날짜별 최솟값)으로 접는다.

**다른 후보와 문제점**
* **후보: 총량·합계 하나로 줄인다**
  * ❌ **판정 근거가 사라진다** — 최솟값 계산(→ 9)도, 요청 기간에 빠진 날짜가 있는지(→ 33)도 날짜별 값이 있어야 알 수 있다.
  * ❌ **합계는 의미가 없다** — 3박 동안 매일 1실씩 남았어도 합이 3이지 3실을 팔 수 있는 게 아니다.

**선택 이유**
1. **요금과 성격이 정반대다.** 요금은 한쪽만 날짜별로 주지만 재고는 **양쪽 다 날짜별로 준다.** 교집합 안에 있으므로 버릴 이유가 없다.
2. **접는 규칙은 도메인 판단이라 정규화 뒤로 미룬다.** 원본을 들고 있어야 규칙을 바꿀 수 있다.
3. **응답에는 접은 값 하나만 나간다** — 클라이언트가 날짜별 재고까지 볼 이유는 지금 스코프에 없다.

### 24. 조식을 요금에 딸린 정보가 아니라 상시 필드로 둔 이유는? 값이 없을 때 항목을 버리지 않는 이유는?

**상황**
: `breakfastIncluded`는 A·B 모두 재고·요금 응답에서만 준다. 요금에 딸린 부가 정보로 볼지, 상품을 구별하는 속성으로 볼지 정해야 했다.

**선택한 구조**
> **표준 모델에 항상 있는 `boolean` 필드.** 공급사가 값을 주지 않으면 `false`로 떨어지되, **요금·재고와 달리 그 항목을 버리지는 않는다.**

**다른 후보와 문제점**
* **후보: 표준에서 빼거나 선택 필드로 둔다**
  * ❌ **총액 비교가 무의미해진다** — 같은 숙소·같은 객실인데 A는 조식 미포함 429,000원, B는 조식 포함 452,000원인 상황이 실제로 나온다. 조식 여부가 없으면 고객은 **조건이 다른 상품**을 그냥 싼 쪽으로 고른다.
* **후보: 요금·재고처럼 값이 없으면 항목을 버린다**
  * ❌ **버릴 만큼 치명적이지 않다** — 총액·재고가 없으면 상품을 팔 수 없지만, 조식 여부를 모르는 것은 조건 하나를 모르는 것이다. 팔 수 있는 상품을 검색에서 지우는 대가가 더 크다.

**선택 이유**
1. **가격 차이를 설명하는 유일한 조건이다.** 총액만으로는 왜 비싼지 알 수 없다.
2. **두 공급사가 모두 주므로 교집합 안에 있다.**
3. **중복 상품을 합치지 않기로 한 결정(→ 14)이 성립하는 근거다** — 두 줄이 나란히 보일 때 무엇이 다른지 이 필드가 답한다.
4. **필수성의 등급을 나눈 결과다** — 상품의 성립 조건(요금·재고)과 비교 조건(조식)을 구분해, 없을 때의 처리를 다르게 뒀다.

### 25. 숙소명·객실명을 공급사 응답이 아니라 DB 스냅샷에서 가져오는 이유는? 두 값이 다르면 무엇을 믿는가?

**상황**
: 숙소명·객실 타입명·최대 인원은 목록 API와 재고·요금 API가 **둘 다** 준다. 검색 응답에 어느 쪽 값을 쓸지 정해야 했다.

**선택한 구조**
> **목록 API 스냅샷을 저장해 둔 DB 값을 쓴다.** 재고·요금 응답의 같은 필드는 통합 VO에 담지도 않아 구조적으로 차단된다(`SearchedRoom.of`가 숙소 정보는 `RoomOption`에서, 요금·재고만 `SupplierRoom`에서 가져온다).

**다른 후보와 문제점**
* **후보: 매 검색마다 재고·요금 응답의 이름을 쓴다(더 최신이다)**
  * ❌ **한 줄 안에서 출처가 갈린다** — `stayId`는 매핑(DB)에서 오고 `stayName`은 공급사 응답에서 오면, 같은 응답 한 줄의 식별자와 이름이 다른 시점의 데이터가 된다.
  * ❌ **`maxOccupancy`는 이미 후보를 고를 때 쓴 값이다**(→ 7). 응답에 다른 값을 실으면 "인원을 수용한다고 골라 놓고 수용 못 하는 인원을 표시"하는 모순이 생긴다.
  * ❌ **응답이 재현되지 않는다** — 같은 조건으로 다시 불러도 이름이 달라질 수 있다.

**두 값이 다르면 무엇을 믿는가**
**DB 값을 믿는다.** 재고·요금 응답의 이름은 읽지 않으므로 애초에 충돌을 감지하지 않는다. 차이는 다음 동기화(최대 하루)에 목록 API 기준으로 정리된다. 이름은 자주 바뀌지 않고, 바뀐 이름이 하루 늦게 반영되는 쪽이 한 응답 안에서 식별자와 이름의 출처가 갈리는 쪽보다 낫다고 봤다.

**선택 이유**
1. **고정값은 한 출처에서만 온다.** 식별자·이름·최대 인원이 전부 같은 스냅샷에서 나와 우리 데이터 안에서 어긋나지 않는다.
2. **자주 바뀌지 않는 값과 매번 바뀌는 값을 성격대로 나눈 결과다**(→ 7).
3. **응답이 재현 가능해진다** — 같은 조건으로 다시 부르면 이름·식별자가 같다.

### 26. 실행은 파일 H2, 테스트는 인메모리로 가른 이유는? `schema.sql` + `validate`를 택한 이유는?

**상황**
: DB는 관계형 하나면 되고 H2를 쓰기로 했다. 실행·테스트에서 어떤 모드로 띄울지, 스키마를 누가 만들지 정해야 했다.

**선택한 구조**
> 실행은 **파일 모드**(`jdbc:h2:file:./data/trip`), 테스트는 **인메모리 + 컨텍스트마다 다른 DB**(`jdbc:h2:mem:${random.uuid}`). 스키마는 **`schema.sql`이 만들고 JPA는 `ddl-auto: validate`로 검증만** 한다.

**다른 후보와 문제점**
* **후보: 실행도 인메모리**
  * ❌ **재시작하면 매핑과 UUID가 전부 날아간다** — "같은 상품은 같은 식별자"(→ 5)가 프로세스 수명만큼만 유효해진다.
* **후보: 테스트도 고정 이름 인메모리 DB 하나**
  * ❌ **캐시된 스프링 컨텍스트끼리 스키마가 충돌한다** — 설정이 다른 컨텍스트가 같은 DB를 잡으면 실행 순서에 따라 깨진다.
* **후보: `ddl-auto: update`(또는 `create`)로 JPA가 스키마를 만든다**
  * ❌ **DDL이 코드에 남지 않는다** — 실제 컬럼 타입·제약·인덱스를 리뷰할 파일이 없고, 나중에 서버형 DB로 옮길 때 기준이 되는 스키마가 없다.
  * ❌ **엔티티와 스키마가 어긋나도 조용히 굴러간다** — `update`는 차이를 알아서 메워 버려서 어긋남이 런타임에야 드러난다.

**선택 이유**
1. **`validate`는 어긋남을 기동 시점에 실패로 바꾼다.** 엔티티와 DDL이 다르면 서버가 뜨지 않는다.
2. **DDL이 파일로 남아 리뷰·이관의 기준이 된다.**
3. **실행과 테스트의 요구가 다르다** — 실행은 영속성, 테스트는 격리와 속도가 필요하다.

### 27. 기동 시 공급사가 죽어 있어도 기동과 검색을 계속하는 이유는?

**상황**
: 기동 시 동기화가 공급사 장애로 실패하면 어떻게 할지, 검색 중 공급사가 죽어 있으면 어떻게 할지 정해야 했다.

**선택한 구조**
> **기동은 계속한다.** 동기화 실패는 로그만 남기고 삼킨다(스케줄 실행도 동일). **검색도 계속한다** — 공급사 실패는 예외로 올리지 않고 `failures[]`에 값으로 모은다.

**다른 후보와 문제점**
* **후보: 기동 동기화가 실패하면 기동을 중단한다(fail-fast)**
  * ❌ **남의 장애로 우리가 못 뜬다** — 공급사가 잠시 죽었다는 이유로 배포가 막히고, 이미 DB에 있는 매핑으로 정상 서비스할 수 있는데도 전체가 내려간다.
* **후보: 검색 중 공급사 실패를 예외로 올린다**
  * ❌ **성공한 공급사 결과까지 버려진다** — "한 곳이 실패해도 나머지로 응답"이라는 요구와 정면으로 어긋난다.

**선택 이유**
1. **외부 연동의 실패는 우리 서비스의 실패가 아니다.** 기존 매핑이 남아 있으면 검색은 정상 동작한다.
2. **동기화 실패 시 기존 값을 유지한다** — 조회가 실패하면 비활성화 로직까지 가지 않아 팔던 숙소가 사라지지 않는다.
3. **실패를 예외가 아니라 값으로 다루면** 부분 성공을 표현할 수 있다(→ 12).

### 28. 목록 항목 하나가 검증에 실패했을 때 그 항목만 빼지 않고 공급사 전체를 건너뛰는 이유는?

**상황**
: 목록 응답의 항목 하나가 검증(빈 코드·빈 이름·최대 인원 1 미만)에 걸렸을 때, 그 항목만 빼고 나머지를 반영할지 공급사 전체를 포기할지 정해야 했다.

**선택한 구조**
> **그 공급사의 동기화 전체를 건너뛰고 기존 DB 값을 유지한다.** 검증은 `SupplierStay`·`SupplierRoomType` 생성자가 하고, 예외가 변환 스트림을 통째로 중단시킨다.

**다른 후보와 문제점**
* **후보: 잘못된 항목만 빼고 나머지를 반영한다**
  * ❌ **판매 중인 숙소가 검색에서 사라진다** — 빠진 숙소는 "목록에 없는 숙소"로 보여 `active=false`로 내려간다(→ 29). 공급사의 일시적 응답 오류가 우리 쪽 판매 중단으로 번역되는 셈이다.
  * ❌ **부분 반영된 상태는 어느 시점의 데이터인지 말할 수 없다** — 일부는 새 값, 일부는 옛 값이 된다.

**선택 이유**
1. **덜 반영하는 것보다 잘못 반영하는 것이 위험하다.** 건너뛰면 DB는 그냥 하루 낡을 뿐이다.
2. **목록 데이터는 잘 바뀌지 않아 다음 주기(최대 하루) 반영으로 충분하다**(→ 8).
3. **검색 경로와 의도적으로 다르게 뒀다** — 검색은 저장이 없어 항목 단위로 빼도 뒷일이 없다(→ 41).

### 29. 목록에서 사라진 숙소를 삭제하지 않고 `active`를 내리는 이유는?

**상황**
: 공급사 목록에서 빠진 숙소·객실을 어떻게 처리할지 정해야 했다.

**선택한 구조**
> **삭제하지 않고 `active=false`로 내린다**(숙소·객실 양쪽). 검색은 활성 숙소만 대상으로 삼는다. 코드베이스에 `delete` 호출이 없다.

**다른 후보와 문제점**
* **후보: 목록에 없으면 행을 지운다**
  * ❌ **UUID가 끊긴다** — 숙소가 잠시 빠졌다 돌아오면 새 행·새 UUID가 생겨 "같은 상품은 같은 식별자"(→ 5)가 깨진다. 이미 밖으로 나간 식별자도 무효가 된다.
  * ❌ **FK로 묶인 객실까지 지워야 한다** — cascade를 켜야 하고, 실수 한 번의 영향 범위가 커진다.
  * ❌ **되돌릴 수 없다** — 공급사 응답 오류로 목록이 비어 왔을 때 복구할 방법이 없다.

**선택 이유**
1. **식별자의 연속성이 이 시스템의 계약이다.** 지우는 순간 그 계약이 깨진다.
2. **비활성화는 되돌릴 수 있다** — 다시 나타나면 같은 행이 `active=true`로 복구된다.
3. **삭제로 얻는 것은 행 몇 개의 공간뿐이다.**

> 객실 `active`는 검색 조회 조건에 쓰지 않는다. 어떤 객실을 팔지는 공급사 재고·요금 응답이 정하므로, 우리가 미리 거르면 공급사가 실제로 파는 객실을 매핑 없는 객실(→ 31)로 떨어뜨린다. 어느 숙소를 물어볼지는 우리 몫이라 숙소 `active`만 본다.

### 30. 값이 바뀔 때만 UPDATE를 하는 이유는? `last_synced_at`을 없앤 이유는?

**상황**
: 동기화는 매일 전체 목록을 받는다. 매번 모든 행을 쓸지, 바뀐 것만 쓸지 정해야 했다. 처음에는 "마지막 동기화 시각"(`last_synced_at`) 컬럼을 두려고 했다.

**선택한 구조**
> 엔티티의 `applyLatestInfo`가 **이름·최대 인원이 같고 이미 활성이면 아무 필드도 건드리지 않고 `false`를 반환한다.** 변경이 없으면 더티 체킹이 걸리지 않아 UPDATE가 나가지 않는다. 시각 컬럼은 `created_at`·`updated_at`(JPA Auditing) 둘뿐이다.

**다른 후보와 문제점**
* **후보: `last_synced_at`을 두고 매 동기화마다 갱신한다**
  * ❌ **매번 전 행이 UPDATE된다** — 바뀐 게 없어도 수천 행의 쓰기가 매일 나간다.
  * ❌ **`updated_at`의 의미가 죽는다** — 동기화 때마다 갱신되니 "언제 실제로 바뀌었나"를 아무 컬럼도 답하지 못한다. 두 컬럼이 사실상 같은 값이 된다.

**`last_synced_at`을 없앤 이유**
`updated_at`과 겹치기 때문이다. 없애고 나니 `updated_at`이 **실제 변경 시각**이라는 정확한 의미를 되찾았고, "언제 마지막으로 동기화가 돌았나"는 행이 아니라 동기화 로그가 답하는 게 맞는 질문이었다.

**선택 이유**
1. **쓰기를 실제 변경으로 제한한다** — 매일 전 행을 쓰지 않는다.
2. **`updated_at`이 진짜 변경 시각이 된다.**
3. **변경 감지를 엔티티 안에 두어** 호출부는 반환값으로 생성·수정·비활성 건수만 세면 된다.

### 31. 매핑에 없는 객실 코드가 검색 응답에 섞여 오면 왜 빼고 로그만 남기는가? 검색 경로에 쓰기를 두지 않은 이유는?

**상황**
: 재고·요금 응답에 우리 매핑에 없는 객실 코드가 섞여 올 수 있다(동기화 이후 공급사가 객실을 추가한 경우). 이때 어떻게 할지 정해야 했다.

**선택한 구조**
> **그 항목만 결과에서 빼고 검색 경로에서는 아무것도 쓰지 않는다.** 반영은 다음 주기 동기화에 맡긴다. 매칭 키는 `(supplier, stayCode, roomTypeCode)` 세 값이다.

**다른 후보와 문제점**
* **후보: 검색 중에 발견하면 그 자리에서 매핑을 만들어 저장한다**
  * ❌ **읽기 경로에 쓰기가 생긴다** — 검색은 트랜잭션 밖에서 공급사를 부르는 구조인데(9) 쓰기가 끼어들면 트랜잭션 경계와 응답 지연이 함께 흔들린다.
  * ❌ **이름·최대 인원의 출처가 갈린다** — 고정값은 목록 API 스냅샷에서만 온다는 규칙(→ 25)이 깨지고, 재고·요금 응답의 이름을 저장하게 된다.
  * ❌ **동시 검색이 같은 코드를 동시에 쓴다** — 유일 제약 충돌 처리를 검색 경로에 넣어야 한다.
* **후보: 매핑에 없는 코드가 오면 그 공급사를 실패로 처리한다**
  * ❌ **정상 상황을 장애로 오인한다** — 공급사가 객실을 하나 추가한 것뿐인데 그 공급사 결과 전체가 사라진다.

**검색 경로에 쓰기를 두지 않은 이유**
검색은 **읽기 전용 경로**여야 부분 실패·타임아웃·취소를 단순하게 다룰 수 있다. 취소된 태스크가 절반만 쓰고 죽는 상황을 고려하지 않아도 되고, 트랜잭션이 공급사 호출을 감싸지 않아도 된다.

**선택 이유**
1. **매핑 갱신의 책임은 동기화 한 곳에 있다.** 두 곳에서 쓰면 규칙이 갈린다.
2. **최대 하루 늦게 반영되는 대가가 작다** — 새 객실 하나가 하루 뒤 노출된다.
3. **임계값 기반 즉시 동기화 트리거는 채택하지 않았다** — 숫자 근거가 없고, 검색 빈도를 재는 상태가 새로 생긴다.

### 32. 저장 실패를 공급사 단위로 격리하고 DB 재시도를 넣지 않은 이유는?

**상황**
: 동기화 중 DB 저장이 실패하면 어떻게 할지, 재시도를 걸지 정해야 했다.

**선택한 구조**
> **공급사마다 예외를 잡아 `error` 로그를 남기고 다음 공급사로 넘어간다.** 트랜잭션이 공급사 단위(`StayManager.sync`)로 열려 실패한 공급사만 롤백된다. **DB 재시도는 걸지 않는다** — 재시도는 공급사 HTTP 호출에만 붙어 있다.

**다른 후보와 문제점**
* **후보: 전체 동기화를 한 트랜잭션으로 묶는다**
  * ❌ **한 공급사의 실패가 전부를 되돌린다** — A가 정상 반영됐는데 B의 저장이 실패하면 A까지 롤백된다.
* **후보: DB 저장에도 재시도를 건다**
  * ❌ **대부분의 저장 실패가 결정적이다** — 제약 위반·타입 불일치는 몇 번을 다시 해도 같은 실패다. 재시도는 실패까지 걸리는 시간만 늘린다.
  * ❌ **재시도를 넣어도 격리는 따로 필요하다** — 재시도를 다 쓰고 나면 결국 같은 자리에서 다음 공급사로 넘어가야 한다.
  * ❌ **내장 H2라 네트워크성 일시 오류가 사실상 없다.**

**선택 이유**
1. **실패 단위가 공급사다** — 호출·검증·저장 어느 단계에서 실패하든 그 공급사만 포기한다.
2. **재시도는 "다시 하면 될 수도 있는 실패"에만 건다**(→ 20). 저장 실패는 그 조건에 맞지 않는다.
3. **다음 기회가 있다** — 다음 주기나 수동 동기화가 같은 일을 다시 한다.

### 33. 요청 기간의 날짜가 하나라도 빠지면 왜 그 항목을 버리는가?

**상황**
: 공급사 응답의 날짜별 데이터가 요청 기간을 다 덮지 않을 수 있다(누락되거나 금액 필드가 `null`인 경우). 이때 어떻게 할지 정해야 했다.

**선택한 구조**
> **그 객실 한 건을 결과에서 통째로 뺀다.** 공급사 전체를 실패로 돌리지 않고, 로그도 남기지 않는다.

**다른 후보와 문제점**
* **후보: 있는 날짜만으로 총액·재고를 계산한다**
  * ❌ **총액이 틀린다** — 3박 중 2박치 금액을 3박 가격으로 내보내게 된다. 고객이 결제 단계에서 다른 금액을 보게 되는, 조용히 틀리는 종류의 오류다.
  * ❌ **최솟값도 틀린다** — 빠진 날이 하필 매진된 날이면 팔 수 없는 상품을 예약 가능으로 표시한다.
* **후보: 공급사 전체를 실패로 처리한다**
  * ❌ **항목 하나 때문에 정상 상품 수백 건을 버린다.**
* **후보: 항목마다 로그를 남긴다**
  * ❌ **공급사 단위 실패 로그가 묻힌다** — 묶음 하나에 상품이 수백 건이라 항목마다 찍으면 진짜 장애 로그가 안 보인다. 기간을 통째로 못 받는 상황이면 그 묶음의 항목이 전부 빠지는데, 그건 결과 건수와 `failures[]`로 드러난다.

**선택 이유**
1. **총액과 재고 둘 다 기간 전체가 있어야만 만들 수 있다.** 재료가 없으면 만들지 않는다.
2. **틀린 값을 내보내느니 안 내보낸다.**
3. **검색 경로의 실패 단위는 항목이다**(→ 41) — 저장이 없어 뒷일이 없다.

### 34. 앞 묶음이 실패했을 때 무엇으로 중단·계속을 가르는가?

**상황**
: 한 공급사의 묶음을 순차로 부르다 중간에 실패하면, 남은 묶음을 계속 부를지 멈출지 정해야 했다.

**선택한 구조**
> **실패 분류가 결정한다.** `AUTH`·`RATE_LIMITED`·`UNAVAILABLE`은 즉시 중단(`stopsRemainingBatches()`), `BAD_REQUEST`·`MALFORMED`·`INTERNAL`은 계속. **어느 쪽이든 앞서 받은 묶음의 상품은 살린다.**

**다른 후보와 문제점**
* **후보: 실패하면 무조건 남은 묶음을 계속 부른다**
  * ❌ **죽은 상대를 계속 때린다** — 서비스가 내려갔으면 남은 59번도 같은 실패인데, 매번 응답 타임아웃 2초씩 소모해 5초 예산을 다 태우고 다른 공급사까지 취소시킨다.
  * ❌ **호출 한도 초과 상태를 더 악화시킨다.**
* **후보: 실패하면 무조건 중단한다**
  * ❌ **묶음 하나만의 문제를 공급사 전체의 문제로 키운다** — 특정 숙소 코드 때문에 응답이 깨졌다면 나머지 묶음은 멀쩡히 받을 수 있다.

**선택 이유**
1. **분류 축이 "다음 묶음도 같은 결과인가"다.** 인증 실패·한도 초과·서비스 불가는 상대의 상태라 다음도 같고, 잘못된 요청·해석 불가·내부 오류는 그 묶음에 딸린 문제일 수 있다.
2. **부분 성공을 최대한 보존한다** — 중단하더라도 이미 받은 묶음은 버리지 않는다.
3. **실패는 공급사당 첫 건만 기록한다**(`putIfAbsent`) — 묶음 여러 개가 실패해도 응답의 `failures[]`는 공급사당 한 줄이다(→ 12).

### 35. 전체 예산을 넘겨 태스크가 취소돼도 앞서 받은 결과를 살리는 구조는?

**상황**
: 검색 전체에 5초 상한을 걸면 초과한 태스크는 취소된다. 그런데 취소된 태스크가 이미 성공시킨 묶음의 결과까지 함께 사라지는 문제가 있었다.

**선택한 구조**
> **태스크가 결과를 `return`하지 않는다.** 태스크 **밖**에 사는 동시성 컬렉션(`ConcurrentLinkedQueue`·`ConcurrentHashMap`)에 묶음마다 즉시 쌓고, 취소 여부는 `Future.isCancelled()`로만 확인해 `UNAVAILABLE / TOTAL_TIMEOUT_EXCEEDED` 실패를 남긴다. `Future.get()`은 부르지 않는다.

**다른 후보와 문제점**
* **후보: 태스크가 결과를 모아 `return`하고 `Future.get()`으로 받는다**
  * ❌ **취소되면 전부 사라진다** — 6개 묶음 중 4개를 성공한 뒤 5번째에서 예산을 넘기면, 태스크 안 지역 변수에 모아 둔 4묶음치가 `return` 문에 도달한 적이 없어 통째로 사라진다. `Future.get()`은 `CancellationException`만 준다. 부분 실패 설계가 하필 전체 타임아웃에서만 깨진다.
* **후보: `@Async` + `CompletableFuture`를 쓴다**
  * ❌ **취소가 동작하지 않는다** — `cancel(true)`로도 실행 중인 스레드를 인터럽트하지 않아 `block()`이 깨지지 않는다. 예산을 넘긴 태스크가 백그라운드에서 남은 묶음을 계속 불러 커넥션과 호출 한도를 축낸다.
* **후보: `StructuredTaskScope`**
  * ❌ **현재 JDK에서 preview API다.**

**선택 이유**
1. **부분 실패 보존이 취소 경로에서도 지켜진다** — "한 공급사가 늦어도 나머지로 응답"이 "한 공급사의 뒷 묶음이 늦어도 앞 묶음은 살린다"까지 확장된다.
2. **`invokeAll(tasks, timeout)`이 이미 마감과 취소를 다 해 준다** — 마감 시각을 태스크에 넘겨 직접 검사하면 같은 일을 손으로 다시 짜는 셈이다.
3. **동시성 타입이어야 한다** — 공급사 태스크들이 같은 컬렉션에 동시에 쓰고 요청 스레드가 읽는다. 대가는 태스크 시그니처가 `Callable<Void>`라 무엇을 만드는지 반환 타입에 안 드러나는 것이다.
4. **태스크 안의 예기치 못한 `RuntimeException`도 반드시 잡는다** — 안 잡으면 `get()`을 부르지 않는 구조라 예외가 조용히 삼켜지고, 그 공급사는 상품도 실패도 없이 사라진다. 그러면 "전부 실패면 502" 판정이 실패 0건을 보고 200 + 빈 목록을 주어 **장애가 "조건에 맞는 객실 없음"으로 둔갑한다.**

### 36. 응답을 숙소·객실 계층이 아니라 객실 단위 1차원 `rooms[]`로 준 이유는?

**상황**
: 공급사는 상품을 "숙소 > 객실 타입" 2단계로 표현한다. 응답도 중첩 구조로 줄지, 평평하게 펼지 정해야 했다.

**선택한 구조**
> **객실 한 건이 원소인 1차원 배열 `rooms[]`.** 원소가 숙소 정보(`stayId`·`stayName`)와 객실 정보를 함께 들고, 한 숙소에 객실이 여럿이면 같은 `stayId`가 여러 번 나온다.

**다른 후보와 문제점**
* **후보: `stays[] > rooms[]` 중첩 구조**
  * ❌ **팔 수 있는 단위와 구조가 어긋난다** — 요금·재고·조식이 전부 객실 타입 단위라, 정작 고객이 고르는 한 건이 배열 안의 배열에 숨는다.
  * ❌ **묶는 기준이 애매해진다** — 같은 숙소가 A와 B 양쪽에서 오면(→ 14) 공급사가 다른 두 상품인데 한 숙소 아래로 묶을지 판단해야 한다. 우리는 합치지 않기로 했으므로 중첩이 그 결정과 충돌한다.
  * ❌ **클라이언트가 항상 펼쳐서 쓴다** — 화면은 객실 카드 목록이라 받자마자 평탄화하게 된다.

**선택 이유**
1. **결과 한 건 = 팔 수 있는 객실 한 건**이라는 정의를 구조가 그대로 드러낸다.
2. **필드명이 `stays`가 아니라 `rooms`인 것도 같은 이유다** — 원소가 숙소가 아니다.
3. **중첩이 필요하면 클라이언트가 `stayId`로 묶을 수 있다** — 반대 방향(펼치기)보다 쉽다.

### 37. 검증을 Request와 VO 두 곳으로 가른 이유는? 중복이 아닌가?

**상황**
: 검색 요청의 제약(날짜 필수, 체크인 < 체크아웃, 과거 날짜 금지, 30박 상한, 성인 1명 이상, 아동 0 이상)을 어디서 검사할지 정해야 했다.

**선택한 구조**
> **필드 하나로 판정되는 제약은 Request의 Bean Validation** (`@NotNull` 날짜·성인, `@Min(1)` 성인, `@Min(0)` 아동) — 400과 `{필드: 사유}`를 한 번에 돌려주고 OpenAPI 스키마에 `required`·`minimum`으로 드러난다.
> **필드 간 규칙과 불변식은 VO 생성자** — `StayPeriod`가 역순(`E1001`)·과거 체크인(`E1002`)·30박 초과(`E1003`)를, `Guests`가 인원 조합(`E1004`)을 본다. 아동 `null`은 VO가 0으로 채운다.

**다른 후보와 문제점**
* **후보: 전부 Bean Validation으로 옮긴다**
  * ❌ **필드 간 규칙에는 클래스 레벨 커스텀 제약이 필요하다** — 별도 Validator 클래스를 만들게 되고, 검증 규칙이 도메인 타입에서 떨어져 나간다.
* **후보: 전부 VO 생성자에서만 본다**
  * ❌ **오류를 하나씩만 돌려준다** — 날짜와 인원이 동시에 비어 있어도 첫 예외에서 끊긴다. 필드별 사유를 한 번에 주는 편이 클라이언트에 낫다.
  * ❌ **OpenAPI 문서에 제약이 안 드러난다.**

**중복이 아닌 이유**
Request는 **HTTP 계약**을 지키고 VO는 **객체 불변식**을 지킨다. HTTP를 거치지 않는 경로(내부 호출·테스트)에서도 `StayPeriod`가 과거 날짜를 거부해야 한다. 같은 규칙을 두 번 쓰는 게 아니라, 서로 다른 경계에서 서로 다른 것을 보장한다.

**각 상한의 근거**
- **체크인 과거 금지** — 지난 날짜는 팔 수 없고, 공급사도 유효 응답을 주지 않는다. 판정은 서버 기본 시간대의 오늘이다.
- **30박 상한** — 기간이 길수록 응답의 날짜별 배열이 커지고 정규화 비용이 는다. 일반 숙박 예약의 실질 상한이기도 하다.
- **성인 1명 이상** — 성인 0명 아동 N명은 예약이 성립하지 않는다. 인원은 `adults + children <= maxOccupancy`로 쓰이므로 둘 다 유효해야 한다.

### 38. 정렬·페이징을 범위 밖으로 두면 `rooms[]` 순서가 흔들리는데, 이를 어떻게 계약에 드러냈는가?

**상황**
: 정렬·페이징이 명시적으로 범위 밖이다. 그런데 결과를 여러 공급사에서 병렬로 모으므로, 아무것도 하지 않으면 `rooms[]` 순서가 호출마다 달라진다. 이 사실을 어떻게 다룰지 정해야 했다.

**선택한 구조**
> **정렬하지 않는다.** 순서는 공급사 태스크가 공유 큐에 쌓은 도착 순서이고 호출마다 달라질 수 있다. 이를 **계약으로 명시하고**, 순서를 단정하는 테스트를 쓰지 않는다.

**다른 후보와 문제점**
* **후보: 범위 밖이니 아무 말도 하지 않는다**
  * ❌ **클라이언트가 우연히 안정적인 순서를 관찰하고 의존한다** — 공급사 응답 속도가 바뀌는 날 화면이 깨지는데 원인을 찾기 어렵다. 명시하지 않은 동작이 사실상의 계약이 되는 전형적인 경우다.
* **후보: 기준을 정해 서버가 정렬한다(총액순 등)**
  * ❌ **범위 밖 기능을 근거 없이 도입하는 것이다** — 무엇으로 정렬할지는 화면이 정할 문제이고, 통화가 섞이면 총액 정렬은 정의조차 안 된다.
* **후보: 도착 순서를 고정하려고 공급사 순서대로 재배열한다**
  * ❌ **정렬을 안 하기로 해 놓고 정렬 규칙을 만드는 것**이고, 그 순서에 의미도 없다(A가 먼저 나올 이유가 없다).

**어떻게 계약에 드러냈는가**
"`rooms[]`의 순서는 보장되지 않는다"를 API 계약 문서에 적고, 테스트에서 순서를 단언하지 않는 것으로 코드에도 못 박았다. 순서가 필요해지면 그때 요청 파라미터로 정렬 기준을 받는다.

**선택 이유**
1. **보장하지 않는 것을 보장하지 않는다고 말하는 것이 계약이다.**
2. **정렬은 화면의 판단이고, 서버가 대신 정하면 되돌리기 어렵다.**
3. **순서를 단정하는 테스트가 없어야** 공급사 응답 속도가 바뀌어도 테스트가 흔들리지 않는다.

### 39. 공통 실행기를 상속이 아니라 조합으로 둔 이유는?

**상황**
: A·B Client가 공유하는 일이 있다 — 요청 실행, 타임아웃, `block()`, 전송 오류 변환, JSON 파싱. 이를 어떻게 공유할지 정해야 했다.

**선택한 구조**
> **`SupplierHttpCaller` 컴포넌트 하나를 각 Client가 생성자 주입으로 나눠 쓴다(조합).** 실행기는 `call`(실행·타임아웃·block·전송 오류 변환)과 `parse`(파싱·빈 본문 처리)만 맡고, **공급사별 성공·실패 판정은 Client가 콜백으로 넘긴다.** 상위에는 fan-out 전용 `SupplierDispatcher`가 따로 있다.

**다른 후보와 문제점**
* **후보: 추상 베이스 클래스(`AbstractSupplierClient`)를 상속한다**
  * ❌ **상속이 구현 세부를 계약으로 굳힌다** — 공급사마다 다른 부분을 추상 메서드로 뚫어 두면, 새 공급사가 그 틀에 안 맞을 때 베이스를 고쳐야 하고 기존 공급사가 영향을 받는다.
  * ❌ **공통 코드가 어디까지 공통인지 흐려진다** — 판정 로직이 슬금슬금 베이스로 올라간다.
* **후보: 데코레이터로 감싼다**
  * ❌ **지금 필요한 것은 감싸기가 아니라 재사용이다** — 실행 전후에 끼워 넣을 관심사가 없다(재시도·서킷은 이미 별도 타입이다).

**선택 이유**
1. **공유하는 것은 "어떻게 부르는가"지 "어떻게 판정하는가"가 아니다.** 조합이 이 경계를 정확히 긋는다.
2. **모니터링·공통 정책을 붙일 자리가 한 곳으로 정해진다.**
3. **한 번의 HTTP 호출**(`SupplierHttpCaller`)과 **N곳 × M묶음의 실행 전체**(`SupplierDispatcher`)를 다른 타입으로 나눠, fan-out의 스레드·타임아웃·취소 처리가 비즈니스 로직에 섞이지 않는다.

### 40. 공급사 본문 코드를 전용 enum으로 두고 공용 `ErrorType`과 합치지 않은 이유는?

**상황**
: B는 장애 상황에서도 HTTP 200을 주고 본문 `resultCode`로만 실패를 알린다(`E503` 등). 이 코드를 어디에 두고 어떻게 분류할지 정해야 했다.

**선택한 구조**
> **본문 코드가 있는 공급사만 전용 enum을 그 공급사 패키지에 둔다**(`b/BResultCode`: 코드 → 내부 분류, 코드 없음은 `MALFORMED`, 모르는 코드는 `INTERNAL`). A는 본문 코드 체계가 없어 enum을 만들지 않고 HTTP 상태로 분류한 뒤 원본 문자열만 보존한다.
> 변환은 **두 단계**다 — `공급사 코드 → SupplierFailureType(내부 분류) → ErrorType(공용 오류)`.

**다른 후보와 문제점**
* **후보: 공급사 코드를 공용 `ErrorType`에 값으로 추가한다**
  * ❌ **전역 enum에 공급사 사정이 섞인다** — 공급사가 늘 때마다 공용 타입이 부풀고, `B_E503` 같은 값이 공급사와 무관한 코드 옆에 놓인다.
  * ❌ **대부분의 공급사 실패는 오류 응답이 되지 않는다** — 검색에서는 `failures[]`의 한 줄이고 동기화에서는 로그일 뿐인데, `ErrorType`은 HTTP 상태와 오류 코드를 들고 있는 타입이다. 성격이 다르다.
* **후보: A에도 형식상 enum을 만들어 대칭을 맞춘다**
  * ❌ **매핑할 코드 체계가 없다** — 값이 없는 enum을 만드는 것이라 코드만 는다.

**선택 이유**
1. **두 단계를 거치면 공급사 코드가 그 공급사 패키지 안에 갇힌다.** 도메인은 내부 분류와 원본 코드 문자열만 본다.
2. **원본 코드를 문자열로 보존해** `failures[].code`와 로그에서 원인을 좁힐 수 있다.
3. **비대칭을 그대로 뒀다** — 공급사마다 실패 표현이 다른 것이 사실이고, 억지 대칭은 없는 구조를 만든다.

### 41. 정규화 실패를 검색에서는 항목 단위로, 목록에서는 공급사 전체로 다르게 다루는 이유는?

**상황**
: 공급사 응답을 표준 모델로 옮기다 실패했을 때의 처리 범위가, 검색과 동기화에서 달라야 하는지 같아야 하는지 정해야 했다.

**선택한 구조**
> **검색(재고·요금): 그 항목만 뺀다.** 변환이 `null`을 돌려주면 컨테이너가 건너뛰고 나머지는 그대로 응답한다.
> **목록(동기화): 그 공급사 전체를 건너뛴다.** VO 생성자가 예외를 던져 변환 전체가 중단되고 기존 DB 값이 유지된다.

**다른 후보와 문제점**
* **후보: 양쪽 다 항목 단위로 뺀다**
  * ❌ **동기화에서 팔던 숙소가 사라진다** — 빠진 항목이 "목록에 없는 숙소"로 보여 비활성화된다(→ 28). 공급사의 응답 오류가 우리 쪽 판매 중단이 된다.
* **후보: 양쪽 다 공급사 전체를 버린다**
  * ❌ **검색에서 상품 하나 때문에 수백 건을 버린다** — 검색은 저장이 없어 그렇게 방어할 이유가 없다.

**차이를 만드는 것은 "뒤에 저장이 있는가"다**
검색 경로에는 **쓰기가 없다.** 항목을 빼도 그 사실이 어디에도 남지 않고 다음 검색이 다시 물어본다. 동기화 경로에는 **쓰기가 있다.** 부분 반영은 DB 상태로 굳고, 빠진 항목이 "사라진 숙소"라는 다른 의미로 해석된다. 같은 종류의 실패라도 뒤에 저장이 있느냐에 따라 안전한 처리가 반대가 된다.

**선택 이유**
1. **되돌릴 수 있는 실패와 굳어지는 실패를 다르게 다룬다.**
2. **검색은 가용성이, 동기화는 정합성이 우선이다.**
3. **목록은 잘 바뀌지 않아 하루 낡아도 되지만, 검색 결과는 지금 필요하다.**

### 42. `block()`을 Netty 스레드가 아니라 가상 스레드의 동기 코드에서 하는 이유는?

**상황**
: `WebClient`의 응답을 값으로 바꾸려면 어딘가에서 `block()`해야 한다. 어느 스레드에서 할지, 실패 판정을 리액티브 체인 안에서 할지 밖에서 할지 정해야 했다.

**선택한 구조**
> **공급사 호출 태스크를 가상 스레드 Executor에 제출하고, 그 태스크 안에서 `block()`한다.** `block()`은 코드 전체에 한 곳(`SupplierHttpCaller`)뿐이다. 응답은 `exchangeToMono(res -> res.toEntity(String.class))`로 **상태와 본문 문자열째** 받고, 상태 분기와 JSON 파싱은 `block()` 이후 동기 코드에서 한다.

**다른 후보와 문제점**
* **후보: `onStatus`·`bodyToMono`로 리액티브 체인 안에서 판정한다**
  * ❌ **판정이 Netty 이벤트 루프에서 돌고 예외가 리액티브 방식으로 흐른다** — 예외 타입과 스택이 섞여 원인을 좁히기 어렵고, B처럼 본문을 봐야 실패를 아는 공급사는 체인 안에서 본문을 다시 꺼내야 한다.
  * ❌ **A(HTTP 상태)와 B(본문 코드)의 판정 구조가 갈라진다** — 같은 자리에서 같은 모양으로 다루기 어려워진다.
* **후보: 요청 스레드에서 공급사를 하나씩 순서대로 `block()`한다**
  * ❌ **병렬 호출이 사라진다**(→ 11).

**선택 이유**
1. **이벤트 루프를 막으면 전체 I/O가 멈춘다** — 가상 스레드 태스크 안에서만 `block()`하도록 자리를 고정했다.
2. **두 공급사의 실패 판정이 같은 모양이 된다** — 상태 → 본문 파싱 → 본문 코드 순서를 A·B가 똑같이 밟는다.
3. **동기 코드라 타임아웃·취소·부분 실패가 읽힌다.**

### 43. `resultCode`는 정상인데 `data`가 `null`인 응답을 실패로 판정한 이유는?

**상황**
: B의 응답에서 `resultCode`가 성공(`0000`)인데 `data`가 `null`로 오는 경우가 있을 수 있다. 성공 코드를 믿을지 정해야 했다.

**선택한 구조**
> **실패로 판정한다** — 성공 코드 확인 **직후** `data`가 `null`이면 `MALFORMED / NULL_DATA`를 던진다. `data`는 있는데 `items`가 `null`인 경우도 `MALFORMED / EMPTY_BODY`로 막는다(A도 같은 패턴).

**다른 후보와 문제점**
* **후보: 성공 코드를 믿고 빈 결과로 처리한다**
  * ❌ **장애가 "결과 없음"으로 둔갑한다** — 이 서버에서 가장 위험한 실패 모드다. 상품이 0건이고 실패도 0건이면 검색은 정상 200 + 빈 목록을 주고, 고객은 "조건에 맞는 숙소가 없다"고 읽는다. 서킷도 재시도도 돌지 않고, 로그에도 아무것도 남지 않는다.
  * ❌ **NPE로 터지거나 조용히 빈 리스트가 된다** — 어느 쪽도 원인을 남기지 않는다.

**선택 이유**
1. **계약 위반은 실패다.** 성공이라면 본문이 있어야 한다. 둘이 모순이면 믿을 근거가 없는 응답이다.
2. **조용한 실패를 시끄러운 실패로 바꾼다** — `failures[]`에 드러나고 로그가 남는다.
3. **`MALFORMED`로 분류해 재시도·서킷 대상에서 뺀다** — 상대는 응답하고 있으므로 건강도 문제가 아니고, 다시 불러도 같은 모순이 올 가능성이 높다.

### 44. 커넥션 풀 50이 사실상 검색 동시성 제한이 되는 것을 감수한 이유는?

**상황**
: `WebClient`의 커넥션 풀 기본값(대기 45s, 크기 `max(코어,8)×2`, 유휴 정리 없음)은 이 워크로드에 맞지 않았다. 풀 고갈과 공급사 지연이 모두 `TIMEOUT` 하나로 뭉개져 원인을 구별할 수 없었다.

**선택한 구조**
> **공급사마다 별도 풀**(`supplier-A`·`supplier-B`), 각각 **최대 50**, 대기 200ms, 유휴 30s. 풀 고갈은 `UNAVAILABLE / POOL_EXHAUSTED`로 따로 분류한다.

**다른 후보와 문제점**
* **후보: 전역 풀 하나를 공유한다**
  * ❌ **한 공급사의 지연이 다른 공급사를 굶긴다** — A가 커넥션을 다 잡고 있으면 B 호출이 풀 대기에 걸린다. "한 곳이 실패해도 나머지로 응답"이라는 설계의 전제가 무너진다.
* **후보: 기본값을 그대로 쓴다**
  * ❌ **대기 45s가 전체 상한 5s보다 훨씬 길어 무의미하다** — 상위 타임아웃이 먼저 잘라 버려 풀 대기가 발현되지 않고, 대신 모든 것이 `TIMEOUT`으로 보인다.
  * ❌ **유휴 정리가 없어 상대가 먼저 끊은 커넥션을 재사용한다.**

**커넥션 풀 50이 사실상 검색 동시성 제한이 되는 것을 감수하는 이유**
한 공급사의 묶음을 순차로 부르므로(→ 11) **검색 한 건이 공급사당 커넥션 1개**를 쓴다. 따라서 풀 50 = 동시에 처리 가능한 검색 약 50건이고, 톰캣이 가상 스레드라 스레드는 얼마든지 늘어나므로 **실질 상한이 이 값에서 결정된다.**

이를 감수하는 이유는 세 가지다. **(1)** 상한이 어딘가에는 있어야 한다 — 없으면 공급사의 호출 한도에 부딪치거나 상대를 밀어 버린다. **(2)** 51번째 요청은 200ms 뒤 `POOL_EXHAUSTED`로 빨리 실패해 **백프레셔로 동작한다.** 무한정 쌓여 전부 느려지는 것보다 낫다. **(3)** 분류가 따로 있어 **우리 쪽 포화임을 알 수 있다** — 공급사 장애와 구별되고, 재시도 대상이 아니다.

50이라는 값 자체는 근거가 약한 잠정값이라 설정으로 뺐다. 실제 트래픽과 공급사의 호출 한도를 알면 다시 정한다.

**선택 이유**
1. **격리가 견고성의 전제다** — 공급사별 풀이 아니면 부분 실패 설계가 자원 층에서 무너진다.
2. **실패를 구별할 수 있어야 고칠 수 있다** — 풀 고갈과 공급사 지연이 같은 코드로 보이면 어느 쪽을 손볼지 알 수 없다.
3. **빠른 실패가 느린 성공보다 낫다** — 200ms 대기는 백프레셔 장치다.

### 45. 재시도를 숙소 목록 동기화에만 건 이유는?

**상황**
: 공급사 호출은 일시적으로 실패한다. 재시도를 걸지, 건다면 어느 경로에 걸지 정해야 했다(선택 구현이다).

**선택한 구조**
> **동기화(목록 조회) 경로에만** 건다. 최초 1회 + 재시도 2회, **2s → 6s 지수 백오프**(총 대기 8s). 대상은 `indicatesSupplierDown()`, 즉 **`UNAVAILABLE`·`INTERNAL`뿐**이다. **검색 경로에는 재시도가 없다.**

**재시도 대상을 둘로 좁힌 이유**
분류마다 "다시 부르면 될 가능성"이 다르다.

| 분류 | 재시도 | 이유 |
|---|---|---|
| `UNAVAILABLE` `INTERNAL` | **한다** | 상대가 일시적으로 내려갔을 수 있다. 시간이 해결하는 종류다 |
| `BAD_REQUEST` | 안 한다 | 우리 요청이 잘못됐다. 다시 불러도 같은 결과다 |
| `AUTH` | 안 한다 | 키가 틀렸거나 만료됐다. 시간이 해결하지 않는다 |
| `RATE_LIMITED` | 안 한다 | **다시 부르면 상대를 더 때린다.** 재시도가 상황을 악화시키는 유일한 분류다 |
| `MALFORMED` | 안 한다 | 상대가 응답은 하고 있다는 뜻이라 건강도 문제가 아니다 |

**다른 후보와 문제점**
* **후보: 검색에도 재시도를 건다**
  * ❌ **5초 예산 안에 재시도할 여유가 없다** — 무응답이면 응답 타임아웃 2s를 이미 썼고, 한 번 더 부르면 4s다. 묶음이 2개만 돼도 전체 상한을 넘겨 **재시도가 성공한 묶음까지 취소시킨다.**
  * ❌ **다음 기회가 곧 온다** — 검색은 초 단위로 다시 들어온다. 실패한 검색 한 건을 살리려고 예산을 태우는 것보다, 빨리 부분 실패로 돌려주고 다음 요청을 받는 편이 낫다.
  * ❌ **부하가 걸린 상대에 트래픽을 2배로 보낸다** — 장애를 키우는 방향이다.
* **후보: "두 공급사가 모두 실패했을 때만" 재시도한다**
  * ❌ **규칙이 뒤집혀 있다** — 양쪽이 동시에 실패하는 상황은 상대 전체 장애이거나 우리 쪽 네트워크 문제라 **재시도 성공률이 가장 낮다.** 반대로 한쪽만 실패한 경우가 일시적일 확률이 높아 재시도 가치가 큰데, 이 규칙은 정확히 그 경우를 건너뛴다.
* **후보: 아예 걸지 않는다**
  * ❌ **동기화는 다음 기회가 24시간 뒤다** — 한 번 놓치면 그날 하루 매핑이 통째로 낡는다.

**선택 이유**
1. **다음 기회까지의 간격이 정반대다.** 검색은 몇 초 뒤에 또 오지만 동기화는 **하루 뒤**다. 재시도의 가치는 이 간격에 비례한다.
2. **동기화는 사용자가 기다리는 호출이 아니다** — 지연 예산에 매이지 않는다. 기동 시 실패하면 기동이 최대 8초 늘어날 뿐이고, 기동 자체는 계속된다(→ 27).
3. **실패 판정 통일에 얹혀 있다**(→ 20) — A의 HTTP 503과 B의 HTTP 200 + `E503`이 **같은 분류로 접혀서 똑같이 재시도된다.** 재시도 코드에 공급사 분기가 한 줄도 없다.
4. **재시도를 다 써도 실패하면 기존 매핑을 그대로 두고 경고만 남긴다** — 조회가 실패하면 비활성화 로직까지 가지 않아 팔던 숙소가 사라지지 않는다.

### 46. 서킷 브레이커를 검색 경로에만 건 이유는?

**상황**
: 공급사 하나가 계속 죽어 있으면, 검색마다 그 공급사를 부르고 응답 타임아웃 2초를 버린 뒤에야 나머지 결과를 내보낸다. 매번 같은 값을 치르는 셈이다(선택 구현이다).

**선택한 구조**
> **검색(재고·요금) 경로에만, 공급사별 인스턴스로** 건다. 개수 기반 창 20, 최소 호출 10, 실패율 50%, **열림 유지 10s**, 반열림 허용 3건. 세는 실패는 재시도와 같은 `UNAVAILABLE`·`INTERNAL`뿐이고 나머지는 창에서 제외한다. **동기화에는 걸지 않는다.**

**목적은 회복이 아니라 빠른 실패다**
브레이커가 공급사를 살려 주지는 않는다. 바꾸는 것은 **우리가 죽은 상대를 기다리는 시간**이다.

| | 브레이커 없음 | 열려 있을 때 |
|---|---|---|
| 공급사 하나가 무응답일 때 검색 응답 시간 | **2.02s** (응답 타임아웃을 다 버린 뒤) | **0.01s** (호출 없이 즉시 접음) |

덤으로 죽은 상대를 계속 때리지 않고, 커넥션이 타임아웃까지 잠겨 있지 않는다.

**기준값의 근거**
- **최소 호출 10** — 표본이 적을 때 한두 번의 실패로 열리지 않게 한다.
- **열림 유지 10s로 짧게** — 검색은 트래픽이 잦아서 **반열림 탐침이 실제 검색 요청으로 그냥 들어온다.** 별도 탐침 스레드가 필요 없다. 길게 잡으면 이미 살아난 공급사의 상품이 그동안 검색에서 빠진다.
- **세는 실패를 좁힌 이유** — 우리 요청이 잘못됐거나(`BAD_REQUEST`) 응답을 해석할 수 없는 것(`MALFORMED`)은 **상대의 건강도가 아니다.** 창에 섞이면 멀쩡한 공급사를 우리 버그로 끊게 된다.

**다른 후보와 문제점**
* **후보: 동기화에도 건다**
  * ❌ **창에 표본이 모이지 않는다** — 하루 1~2회 호출이라 최소 호출 10을 채우는 데 며칠이 걸린다.
  * ❌ **상태가 의미를 잃는다** — 다음 호출이 24시간 뒤인데 10초 뒤 반열림이 무슨 뜻인지 말할 수 없다.
* **후보: 직접 구현한다**
  * ❌ **상태 전이와 동시성을 다시 검증해야 한다** — 라이브러리는 이미 검증돼 있고, 스프링 스타터 없이 코어 모듈만으로 충분하다.
* **후보: 열렸을 때 전용 오류 응답을 준다**
  * ❌ **응답 계약이 갈라진다** — 클라이언트가 서킷이라는 우리 내부 사정을 알아야 한다.

**열렸을 때 기존 경로를 그대로 타게 한 것**
호출을 건너뛰고 `UNAVAILABLE / CIRCUIT_OPEN` 실패를 던진다. 그러면 **응답 계약이 전혀 바뀌지 않는다** — `failures[]`에 `code=CIRCUIT_OPEN`으로 한 줄 실리고, `UNAVAILABLE`이라 남은 묶음도 부르지 않으며(→ 34), 양쪽이 다 열리면 502가 된다(→ 13). 새 분기가 하나도 필요 없다.

**선택 이유**
1. **경로마다 호출 빈도가 달라 브레이커의 전제가 달라진다.** 검색은 표본이 쌓이고 동기화는 쌓이지 않는다.
2. **재시도와 정확히 반대 경로에 걸린다** — 검색은 "기다릴 시간이 없으니 빨리 접는다", 동기화는 "다음 기회가 머니 더 해 본다". 두 정책이 같은 판정 기준(`indicatesSupplierDown()`)을 공유하면서 반대 방향으로 쓰인다.
3. **기존 부분 실패 경로에 얹혀 계약이 안 바뀐다.**
