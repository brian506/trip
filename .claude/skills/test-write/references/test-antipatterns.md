# 테스트 안티패턴 체크리스트

`test-review` 에이전트가 테스트 코드를 검토할 때 번호 순서대로 대조한다.
대상은 "통과하지만 버그를 못 잡는" 테스트다. 통과 여부는 `./gradlew build`가 이미 확인한다.

이 프로젝트의 테스트는 `@DisplayName` 자연어 문장이 명세이고, 사용자가 선택한 상황만 구현한다.
아래 항목은 선택된 테스트가 문장을 제대로 검증하는지 보는 기준이다. 선택되지 않은 상황을 요구하는 근거로 쓰지 않는다.

---

## 1. `any()`로 인자를 흘리지 않는다

> 호출 검증은 쓰지 않는다(`test-conventions.md` 검증 범위). 이 항목이 남아 있는 자리는
> MockWebServer의 `takeRequest()` 단언과, **반환값·예외를 단언할 때 값을 고정하라**는 요구다.
> 아래 "반드시 값을 고정한다" 목록은 어느 쪽이든 그대로 적용된다.

`verify`/`then`에서 인자를 `any()`, `anyString()`으로 두면 호출 여부만 검증된다.
인자가 뒤바뀌거나 엉뚱한 값이 들어가도 통과한다.

```java
// 나쁨 — 체크인·체크아웃을 뒤바꿔도 통과한다
then(supplierClient).should().search(anyList(), any(), any());

// 좋음 — 값을 고정한다
then(supplierClient).should().search(List.of(HOTEL_CODE), CHECK_IN, CHECK_OUT);
```

객체를 통째로 넘길 때는 `ArgumentCaptor`로 열어서 필드별로 단언한다. 특히 다음은 반드시 값을 고정한다.

- 공급사 코드와 내부 식별자
- 체크인과 체크아웃
- 성인과 아동 인원
- 금액과 통화

## 2. 테스트 데이터를 서로 다르게 준다

같은 값을 두 자리에 넣으면 스왑 버그가 드러나지 않는다.

```java
// 나쁨 — 성인과 아동이 같아 뒤바뀌어도 통과
new Guests(2, 2);

// 좋음
new Guests(2, 1);
```

기본값과 같은 값으로 "변경"을 테스트하지 않는다. 핸들러 본문을 지워도 통과한다.

## 3. 스텁한 값을 되받는 동어반복을 만들지 않는다

```java
// 무의미 — mock이 준 걸 그대로 비교한다
given(manager.find(code)).willReturn(expected);
assertThat(service.get(code)).isEqualTo(expected);
```

이 단언은 문장이 주장하는 동작이 깨져도 통과한다. 문장이 주장하는 결과를 mock 반환값이 아닌 대상의 동작으로 확인한다.
같은 이유로 스텁한 호출을 그대로 verify하지 않는다 (`given(x.f()).willReturn(v)` 후 `then(x).should().f()`).
어떤 상황을 테스트할지는 사용자가 고른다. 이 항목을 근거로 선택된 테스트를 빼라고 지적하지 않는다.

## 4. 모순된 mock 조합을 만들지 않는다

실제로 동시에 성립할 수 없는 상태를 stub하면, 프로덕션에서 절대 성공할 수 없는 경로가 초록불로 덮인다.
스텁을 여러 개 세울 때 "이 상태가 실제로 가능한가"를 자문한다.
같은 데이터를 두 경로로 조회하는 코드라면 두 스텁이 서로 모순되지 않아야 한다.

## 5. 부수효과를 검증한다 — HTTP 상태만 보지 않는다

API 테스트에서 200과 `resultType: SUCCESS`만 확인하면 서비스가 아무 일도 안 해도 통과한다.

- 저장 → 저장된 행을 다시 읽어 값이 반영됐는지
- 검색 → 응답 본문의 식별자, 요금, 재고, 부분 실패 표시가 기대값인지
- 실패 → `is4xxClientError()` 대신 정확한 상태와 에러 코드

좋은 예: `.expectStatus().isBadRequest()` + `jsonPath("$.error.errorCode").isEqualTo("E400")`

## 6. 절대 실패할 수 없는 단언을 쓰지 않는다

- 메서드 안에서 `new`로 만들어 반환하는 객체에 `isNotNull()`
- `UUID.randomUUID()`로 채우는 필드에 `isNotBlank()`
- `now()`로 채우는 필드에 `isNotNull()`
- 본문이 로그 한 줄인 메서드에 `doesNotThrowAnyException()`
- 빈 컬렉션에 대한 `allMatch`/`noneMatch`. AssertJ에서 무조건 통과한다. 먼저 `hasSize(n)`으로 비어 있지 않음을 고정한다.

## 7. 순서가 결과에 영향을 주면 `InOrder`로 고정한다

> 호출 검증을 쓰지 않으므로 이 항목은 적용되지 않는다(`test-conventions.md` 검증 범위).
> 순서가 결과에 영향을 준다면 그 결과를 반환값으로 단언한다.


`then(a).should()`와 `then(b).should()`는 순서를 고정하지 않는다.
검증이 부수효과보다 먼저 일어나야 한다면 `InOrder`로 고정하고,
검증 실패 시 부수효과가 일어나지 않았는지 `never()` 반례를 넣는다.

## 8. 경계 문장은 정확히 그 경계값을 쓴다

경계 상황 문장이 선택됐다면 입력값이 정확히 그 경계여야 한다.
"체크아웃이 체크인 다음 날이면"인데 사흘 뒤 날짜를 넣으면 경계가 검증되지 않는다.

- 한도 N: 문장이 "N이면"이면 정확히 `N`, "N을 넘으면"이면 정확히 `N+1`
- 날짜: 체크인 당일, 체크아웃 전날, 체크아웃 당일처럼 문장이 가리키는 날짜 그대로
- 경계 반대편 상황이 선택되지 않았다면 지적하지 않고 누락 상황 제안으로만 올린다

## 9. 비동기·병렬 호출 검증을 즉시 끝내지 않는다

별도 스레드나 Reactor 스트림에서 도는 코드에 `verify(mock, never())`를 즉시 걸면,
작업이 시작도 하기 전에 검증이 끝나 무조건 통과한다.

- 스트림은 `StepVerifier`로 완료·에러 신호까지 검증하거나, 결과를 받은 뒤 단언한다.
- 타임아웃 테스트는 실제로 지연을 발생시키고, 제한 시간 안에 끝났는지와 결과를 함께 단언한다.
- 지연·무응답을 만든 테스트는 끝날 때 반드시 정리한다.

## 10. `@DisplayName`이 주장하는 것을 실제로 단언한다

이름이 "부분 실패를 표시한다"인데 단언이 HTTP 200뿐이거나,
"예약 불가 상품은 0으로 노출한다"인데 재고 단언이 없는 경우다.

이름과 단언이 어긋나면 이름을 고치는 게 아니라 단언을 추가한다.
문장은 사용자가 선택한 명세이므로 테스트에 맞춰 바꾸지 않는다.

## 11. 문장에 없는 것을 단언하거나 구현에서 기댓값을 가져오지 않는다

- 문장에 없는 조건을 given에 몰래 추가하면, 문장이 말하는 상황이 아니라 다른 상황을 검증하게 된다.
- 문장에 없는 결과를 단언하면 구현 세부에 묶여 명세와 무관한 변경에도 깨진다.
- 기댓값이 문장이나 스펙에 없고 현재 구현 출력과만 일치하면 구현에서 역산한 것이다. 버그를 정답으로 고정한다.
- 문장만으로 값을 정할 수 없었다면 구현을 보는 대신 사용자에게 물었어야 한다.
