# Test Write

## 원칙

- 테스트는 `@DisplayName`에 적힌 자연어 문장을 명세로 삼는다. 구현 코드를 보고 쓰지 않는다.
- 구현 코드에서 확인해도 되는 것은 호출에 필요한 시그니처뿐이다. 패키지, 클래스·메서드 이름, 파라미터·반환 타입, 생성자, `ErrorType` 이름이 해당한다.
- 메서드 본문의 분기, 계산, 상수값을 읽고 상황이나 기댓값을 만들지 않는다. 그렇게 만든 테스트는 버그를 정답으로 고정한다.
- 사용자가 선택한 상황만 구현한다.
- `src/main/`은 수정하지 않는다. 구현 수정은 `/feature`가 맡는다.

## Step 1: 대상 확인

사용자가 말한 기능과 관련 이슈를 확인한다.

```bash
gh issue view <N>
```

## Step 2: 스펙 정리

대상 기능의 입력, 출력, 제약을 3~5줄로 정리해 제시한다.
출처는 사용자 설명, 이슈, `JOURNAL.md`의 결정, 공급사 스펙 요약이다. 출처가 없는 항목은 추측하지 말고 묻는다.

## Step 3: 상황 제시 — 정상 / 경계 / 예외

스펙에서 자연어로 나타날 수 있는 상황을 세 분류로 뽑아 번호를 붙여 제시한다.
각 항목은 그대로 `@DisplayName`이 될 문장이며, 조건과 기대 결과를 함께 담는다.

| 분류 | 무엇 |
|------|------|
| 정상 | 스펙이 규정한 대표 흐름 |
| 경계 | 한도, 범위, 날짜의 끝. 통과하는 끝과 막히는 끝을 각각 별도 항목으로 |
| 예외 | 규칙 위반, 외부 공급사 실패. 기대 결과(에러 코드, 부분 실패 표시 등)를 문장에 포함 |

```
[정상]
1. 공급사 두 곳이 모두 응답하면 두 공급사의 상품을 합쳐 반환한다
[경계]
2. 체크아웃이 체크인 다음 날이면 1박으로 검색한다
3. 체크아웃이 체크인과 같은 날이면 요청을 거부한다
[예외]
4. 공급사 한 곳이 응답하지 않으면 나머지 결과와 부분 실패 사실을 반환한다
```

분류마다 빠짐없이 뽑는다. 후보가 없는 분류는 이유를 적는다.

## Step 4: 사용자 선택 — 선택 전까지 코드 작성 금지

- 구현할 번호를 사용자가 고르게 한다. 분류별 후보가 4개 이하이면 분류마다 AskUserQuestion(multiSelect)으로 묻고, 더 많으면 번호로 답해 달라고 요청한다.
- 사용자가 문장을 고치거나 상황을 추가하면 반영한 목록을 다시 확인받는다.
- 선택되지 않은 항목은 쓰지 않는다. 임의로 추가하지 않는다.

## Step 5: 작성 — DisplayName 문장이 명세

- 선택된 문장을 `@DisplayName`에 그대로 쓴다.
- 테스트 본문은 그 문장만으로 given, when, then을 구성한다.
  - 문장이 주장하는 결과는 모두 단언한다.
  - 문장에 없는 조건이나 결과를 단언하지 않는다.
- 기댓값은 문장과 Step 2 스펙에서 가져온다.
- 문장만으로 입력값이나 기댓값을 정할 수 없으면 구현을 열어보지 말고 사용자에게 묻는다.
- 작성 중 `references/test-antipatterns.md`를 참고한다.
- 테스트 종류별 위치, 단위·통합 방식, 형식은 `references/test-conventions.md`를 따른다.

## Step 6: 실행

단위 테스트는 `test`, `@IntegrationTest`를 붙인 통합 테스트는 `integrationTest`로 실행한다.

```bash
./gradlew test
./gradlew integrationTest
```

- 시그니처를 잘못 써서 난 컴파일 오류는 테스트 쪽 호출을 고친다.
- 단언 실패는 테스트를 구현에 맞춰 고치지 않는다. 실패한 문장, 기대값, 실제값을 사용자에게 보고한다.
- 구현 버그인지 문장이 틀렸는지는 사용자가 판단한다.

## Step 7: 검증 — 별도 컨텍스트

직접 자기검토하지 않는다. `test-review` 에이전트를 호출한다.

prompt에 포함할 것:
- 테스트 파일 경로
- 사용자가 선택한 DisplayName 문장 목록
- Step 2 스펙
- 대응하는 `src/main` 클래스 경로

처리:
- `판정: 수정 필요`면 지적을 반영하고 다시 실행한다.
- 누락 상황 제안은 바로 구현하지 않는다. Step 4처럼 사용자에게 선택받는다.
- 수용하지 않는 지적은 근거를 `JOURNAL.md` AI 활용 항목에 적는다.
